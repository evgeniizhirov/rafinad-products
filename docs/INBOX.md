# Входящие задачи Bitrix → Gmail → Rafinad

## Поведение пилота

Письмо сохраняется как событие Inbox и автоматически создаёт RF. Классификация определяется административным справочником типов; неизвестный тип создаёт внутреннюю задачу. Безопасные изменения полей источника синхронизируются с RF, ручные правки сохраняются. Предпросмотр и ручная привязка остаются для исключений. Полное описание актуального поведения — в [EXTERNAL_TASK_TYPES.md](EXTERNAL_TASK_TYPES.md).

Администраторы имеют доступ ко всему Inbox. Для остальных нужны роль `product` и активное членство в продуктовом подразделении. Персональные API-ключи не получают доступа к новым API Inbox. Права существующих RF, включая доступ администраторов и ключей, не изменены.

Описание источника ограничено 100 000 единицами UTF-16, описание RF — 20 000 (для обычной кириллицы одна буква равна одной единице, некоторые emoji занимают две). Превышение вызывает ошибку: обрезания нет. Оригинал остаётся в Inbox; для RF можно подготовить короткую редакцию. HTTP-запрос целиком ограничен 500 000 байтами UTF-8; Gmail-скрипт проверяет тот же предел перед отправкой. Вложения не передаются.

Опрос Gmail и heartbeat — каждые 5 минут; предупреждение о пропавшем heartbeat — через 20 минут. Worker обрабатывает очередь каждую минуту, до 25 событий за запуск. Обработка имеет lease 120 секунд и до 8 попыток, затем требуется ручной разбор. На стороне Gmail также не более 8 попыток доставки с увеличивающейся задержкой. Автоматической очистки исходников и внешних уведомлений нет.

## Поддерживаемое письмо

Тема: `RAFINAD_SYNC | BITRIX | CREATE | 402775`.
Вместо CREATE поддерживаются UPDATE, BLOCKED, POSTPONED, DONE и REOPENED.

Парсер принимает текстовое представление письма с метками:

```text
ID задачи Bitrix: 402775
Ссылка на задачу: https://my.kokocgroup.ru/workgroups/group/2669/tasks/task/view/402775/
Название: Тестовая
Дата создания: 14.10.2026 11:43:07
Описание: Проверка отправки триггера в статусе бэклог
Тип задачи: Rafinad
Приоритет Bitrix: N
Связанные задачи:
Постановщик: user_4158
Крайний срок: 22.10.2026 10:00:00
```

Допускаются многострочные значения и перенос ссылки. ID в теме, теле и ссылке должны совпадать; хост ссылки и отправитель должны соответствовать подключению. Повтор известной метки считается неоднозначностью и отправляет событие на разбор. HTML не исполняется; Gmail отдаёт `getPlainBody()`, а UI выводит текст. Тестовый образец переписан со скриншота: фактическое текстовое представление реального письма необходимо проверить при первом запуске.

`Rafinad`, `N`, `user_4158` и даты сохраняются как значения источника. Пользователь Bitrix не сопоставляется автоматически с сотрудником Rafinad. У письма нет версии изменения: время получения и дата создания не доказывают порядок UPDATE. Поэтому изменение уже заполненного поля становится конфликтом с выбором «оставить текущее / применить из письма». Отсутствующее поле не стирает старое. Для других интеграций предусмотрен адаптер `canonical_v1` с явными `clear_fields` и порядком по версии/времени источника.

## Запуск Worker

1. Применить миграции D1, включая `migrations/0019_inbox.sql` и `migrations/0020_external_task_types.sql`, до выкладки нового Worker. Для обычного окружения репозитория: `npm run db:migrate:remote`. Seed в существующую базу не загружать.
2. Собрать и развернуть приложение обычным процессом проекта. По умолчанию `INBOX_INGEST_ENABLED=0`, приём и обработка выключены.
3. Администратором открыть «Входящие задачи → Журнал синхронизации», создать подключение с уникальным ID (например `bitrix-gmail`), порталом `my.kokocgroup.ru` и отправителем `robot@my.kokocgroup.ru`. Новое подключение выключено.
4. Установить Worker secret `INBOX_INGEST_KEYS` через `wrangler secret put INBOX_INGEST_KEYS`. Значение — JSON-словарь ID подключения → случайный секрет длиной не менее 32 символов. Например форма значения: `{"bitrix-gmail":"<случайный секрет>"}`. Не сохранять реальное значение в Git, документации или логах.
5. При запуске пилота выставить `INBOX_INGEST_ENABLED=1` в конфигурации окружения и включить подключение в журнале. Учесть, что последующий deploy с исходным значением `0` снова выключит приём.

Машинный секрет разрешает только `POST /api/integrations/events` и `POST /api/integrations/heartbeat`, с заголовками `Authorization: Bearer …` и `X-Integration-Id`. Он не даёт чтение Inbox или редактирование RF. Лимит — 120 запросов в минуту на подключение. Смена секрета требует одновременно обновить Script Properties; для остановки достаточно выключить подключение или общий флаг. Исходники остаются в базе.

## Подключение существующего Gmail

1. В аккаунте, куда уже приходят письма, создать проект Google Apps Script. Скопировать `integrations/gmail/Code.gs` и `appsscript.json`. Включить Advanced Gmail service (Gmail API v1).
2. В Script Properties заполнить:

| Свойство | Значение |
|---|---|
| `RAFINAD_URL` | HTTPS-адрес приложения без пути, например `https://roadmap.example` |
| `INTEGRATION_ID` | ID созданного подключения |
| `INTEGRATION_SECRET` | Тот же секрет, что в Worker |
| `MAILBOX_ID` | Постоянный уникальный идентификатор этого ящика, например `product-inbox-1` |
| `ALLOWED_SENDER` | `robot@my.kokocgroup.ru` |

3. Выполнить `syncRafinadInbox` вручную и пройти авторизацию Google. Скрипт читает почту, ставит служебные метки и отправляет текст подходящих писем на указанный Worker. Он не отправляет письма и не удаляет сообщения.
4. В журнале Rafinad проверить heartbeat, приём и разбор первого письма; сверить все исходные поля с письмом, особенно многострочное описание. Затем выполнить `installRafinadTrigger` для опроса каждые 5 минут.

Скрипт ищет письма с `subject:RAFINAD_SYNC` без меток `Rafinad/Delivered` и `Rafinad/Error`, в том числе старые письма; ограничение дат не задано. Обрабатывает максимум 25 сообщений за запуск. Метки ставятся на отдельные сообщения, поэтому новый UPDATE в старой цепочке не теряется. Стабильный ключ доставки состоит из MAILBOX_ID и Gmail message ID; MAILBOX_ID нельзя произвольно менять при повторной установке.

Проверка From — фильтр формата, а не криптографическая аутентификация отправителя. Доверенной границей служат настроенный почтовый ящик и секрет доставки. Отдельная проверка DKIM/SPF адаптером не выполняется.

## Повторы и журнал

- HTTP 2xx с `accepted:true` и `event_id` означает сохранение события, но не завершение разбора. Ошибочное содержимое может быть принято в карантин. Gmail помечает доставку только после такого подтверждения.
- При потере ответа повтор с тем же delivery_id безопасен; изменённое содержимое с тем же ключом отклоняется. Для интеграций с настоящим source_event_id поддерживается отдельная дедупликация события. Для текущего письма такой ID не выдумывается.
- Ошибка разбора или конфликт видны в журнале Inbox. После исправления парсера можно повторить серверную обработку; конфликт разрешается по отдельным полям. Повтор не создаёт новую RF и не создаёт повторную RF.
- Если сообщение не дошло до сервера, оно получает `Rafinad/Error` после постоянной ошибки или исчерпания попыток. `RF_DIAGNOSTICS` в Script Properties хранит последние 30 записей с ID сообщения, кодом и временем, без текста и секретов. После устранения причины `retryRafinadErrors` снимает служебные метки у первых 50 ошибочных сообщений. Для уже принятого сервером карантина нужна также кнопка повтора в Inbox.
- Preview и подтверждение проверяют версии Inbox и целевой RF. Создание RF, внешняя ссылка, решение Product и запись операции фиксируются одной транзакцией. Устаревший предпросмотр нужно открыть заново. При слиянии RF связь Inbox переносится; при удалении RF исходник и решение сохраняются, автоматического повторного создания нет.

## Проверка перед пилотом

Локально: `npm test`, `npm run typecheck`, `npm run typecheck:client`, `npm run build`.
Тесты Inbox покрывают доступ, повторы, карантин, lease, порядок событий, пределы текста, конфликтующие подтверждения и откат транзакции. Gmail проверяется в изолированном окружении с имитацией Google API. Эти тесты не заменяют первый прогон реального письма через Gmail и развёрнутый Worker/D1.

# Автоматические RF и справочник внешних типов

Эта корректировка заменяет обязательное подтверждение Product из первоначального ТЗ Inbox.

## Классификация и доступ

В «Администрирование → Типы внешних задач» администратор добавляет, изменяет, включает, отключает и удаляет пары `source` + `type_value`. Сопоставление точное, с учётом регистра и пробелов; значение типа в исходнике не заменяется нормализованным названием. Пустое значение не разрешено в справочнике.

Активное совпадение создаёт общую RF: `is_product_internal=0`, `visibility=internal`. Здесь `internal` — существующая видимость для сотрудников, а не флаг скрытой задачи Product. Публикация анонимным посетителям автоматически не выполняется. Общая RF появляется в общем бэклоге, приоритетах и других общих представлениях; попадание на временную диаграмму по-прежнему зависит от дат и планирования.

Любое другое значение, включая отсутствие типа, создаёт RF с `is_product_internal=1`, `visibility=internal`. Ручная классификация не требуется. Дашборд «Внутренние задачи» показывает эти же RF, количество закрытых задач, оценки и учтённый факт. Действующие проверки `canSeeFeature`, `loadWorld` и прав редактора исключают их из общих списков, поиска, графиков, отчётов и API для других подразделений. Администраторы и Product сохраняют существующие права; доступ к сырому Inbox по-прежнему требует сессию администратора либо Product с активным членством в продуктовом отделе.

## Создание и синхронизация

Сохранение снимка Inbox, создание RF, связи, фиксация владельца полей и результат обработки выполняются одной транзакцией. Повтор delivery_id или события не создаёт вторую RF. Уникальность внешней задачи: источник + экземпляр источника + внешний ID. Похожие названия не являются основанием для объединения. Совпадение внешней ссылки с существующей RF — исключение для явной привязки через Inbox.

Автоматически обновляются название, описание, постановщик и исполнитель, пока значение RF совпадает с последним применённым значением источника. Если сотрудник изменил поле непосредственно в RF, интеграция сохраняет его и фиксирует это в приватном журнале. Приоритет, оценки, голоса, этапы и RF-статус не выводятся автоматически из внешних статусов. Состояния и сроки внешних систем показаны отдельно в карточке RF. Туда не передаются тело письма, конфликты, диагностика или приватная история Inbox.

При изменении типа источником классификация вычисляется снова. Изменение одного лишь справочника не переклассифицирует старые RF даже при очередном UPDATE других полей. Для массового пересчёта администратор запускает «Пересчитать существующие — предпросмотр», проверяет перечень и явно подтверждает изменение доступа. Версии справочника, Inbox и RF защищают от устаревшего подтверждения. Один пакет ограничен 500 автоматически управляемыми задачами; для большего объёма нужна отдельная миграция с пакетированием, операция не выполняется частично.

При переводе общей задачи во внутреннюю она исключается из релиза и спринта, снимается фокус релиза; оценки и голоса сохраняются. Это необходимо, поскольку действующая модель запрещает внутренние задачи в общих релизах. Изменение классификации сохраняется в истории RF, а исходный тип и подробности — в приватной истории Inbox.

Порядок определяется версией или временем изменения источника, если подключение настроено на них. Без достоверного порядка конфликтующие поля остаются на ручной разбор. Разрешение конфликта применяет выбранные данные также к принадлежащим источнику полям RF и к классификации. Неизвестный тип сам по себе конфликтом не является. Для писем Bitrix из предоставленного образца надёжной версии нет.

Связать две системы с одной RF можно явной привязкой исключения или штатным слиянием RF. У общей RF один владелец синхронизируемых полей. При слиянии сохраняется владелец целевой RF; вторичный источник обновляет свой снимок и отдельное внешнее состояние, но не перезаписывает целевую RF. Автоматического выбора «кто главнее» между Jira и Bitrix нет.

## Миграции и совместимость

Применить `0019_inbox.sql`, затем `0020_external_task_types.sql` перед выкладкой Worker. Миграция создаёт пустой справочник; не добавляет разрешённые типы и не меняет видимость существующих RF. Существующие ручные связи Inbox сохраняются без передачи владения полями интеграции. Новые события могут автоматически создать RF для ранее не принятой входящей; ранее отклонённые и удалённые RF не восстанавливаются автоматически.

Пределы сохраняются: 100 000 единиц UTF-16 в исходном описании, 20 000 в RF и 500 000 байт запроса. Длинный исходник сохраняется, а автоматическое создание/обновление RF выдаёт `rf_description_too_long`, без обрезания. Для такого исключения остаётся ручная подготовка сокращённого текста. Карантин, повторы, heartbeat и запрет очистки остаются в силе.

## Jira и другие источники

В подключении можно выбрать источник `jira` или другой код и способ «События интеграции». Отправитель использует тот же машинный API с адаптером `canonical_v1`; пример тела POST `/api/integrations/events`:

```json
{
  "delivery_id": "jira-delivery-100",
  "source_event_id": "jira-event-100",
  "event": {
    "schema_version": 1,
    "external_task_id": "PROJ-123",
    "event_type": "CREATE",
    "source_event_version": 1,
    "payload_mode": "patch",
    "payload": {
      "title": "Новый отчёт",
      "description": "Ожидаемый результат",
      "source_task_type": "Story",
      "external_status": "To Do",
      "source_url": "https://jira.example/browse/PROJ-123"
    }
  }
}
```

Заголовки и секреты описаны в [INBOX.md](INBOX.md). `source_event_version` должен быть версией самого изменения, а не временем доставки; при использовании `source_event_at` подключение настраивается на `time`. Сырой Jira webhook требуется преобразовать к этому контракту на стороне подключённого механизма интеграции. Новый доступ к конкретному Jira-порталу или рабочему Gmail этой локальной реализацией не устанавливался.

## API

- `GET/POST /api/admin/external-task-types` — список и добавление.
- `PATCH/DELETE /api/admin/external-task-types/:id` — изменение/удаление с `version`.
- `POST /api/admin/external-task-types-preview` — перечень изменений и hash.
- `POST /api/admin/external-task-types-apply` — `{hash, confirm:true}`.
- `GET /api/internal-tasks?q=...` — внутренние RF и показатели, только редакторам.

Новые административные API недоступны персональным API-ключам. Существующий доступ ключей к RF определяется прежними scope и ролью.

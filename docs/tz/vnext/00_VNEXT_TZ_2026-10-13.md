# Rafinad Product Roadmap — единое ТЗ на следующую итерацию

**Дата фиксации:** 13.10.2026  
**Репозиторий:** https://github.com/evgeniizhirov/rafinad-products  
**Текущий production:** https://products-roadmap.ezhirov-es.workers.dev  
**Исполнитель:** Claude Code  
**Статус:** функциональные решения разделов 1–6 согласованы; идеи раздела 7 не включать в реализацию без дополнительного подтверждения.

## 0. Общие условия и важные уточнения

Текущее приложение уже работает в production. Перед реализацией прочитать актуальную ветку `main`, миграции, клиентские компоненты, backend-роуты и тесты. Не полагаться только на это ТЗ для названий маршрутов и полей. Никаких прямых изменений production, данных D1, секретов, merge или деплоя без отдельного разрешения владельца. Работать небольшими PR с миграциями и тестами. Перед изменениями проверить незавершённую параллельную работу по MCP-интеграции (её делает Codex); не создавать конфликтующие изменения и не менять её код без согласования.

**Принцип:** Roadmap — продуктовый инструмент для двух аудиторий. Бизнес выдвигает предложения, влияет на приоритеты и видит понятный план результатов. Продуктовая команда в отдельном планировщике управляет всей внутренней работой, оценками, спринтами и ресурсами. **Основной Гант в «Обзоре» общий и одинаковый для обеих аудиторий**: одинаковая структура, сроки, группы, этапы и цветовая логика, а не две независимые диаграммы. Данные общего Ганта — только согласованные для бизнес-просмотра; закрытые и внутренние задачи в нём не показывать даже продуктовой команде. Внутренние задачи доступны продуктам в собственном планировщике. Проверки видимости выполнять на сервере, включая агрегаты и экспорт.

## 1. Удалить ненужный модуль «Офферы»; создать «Предложения»

### 1.1. Удаление «Офферов»

Существующий раздел «Офферы» (`client/src/pages/Offers.tsx`, API `/api/offers`, сущности `offers` и `feature_offers`) представляет каталог партнёрских офферов. **Этот каталог не нужен** и не является системой бизнес-предложений. Не переименовывать прежнюю таблицу `offers` в `proposals` — это разные сущности.

- Удалить «Офферы» из меню, форм, фильтров задач, импортных шаблонов и других пользовательских сценариев, где они больше не нужны.
- До удаления схемы выполнить инвентаризацию ссылок, существующих записей, зависимостей, данных и конфигураций импорта; если данные есть, не уничтожать их без одобрения и подготовить план миграции/архивирования.
- Сохранить работоспособность остальных разделов. Не переиспользовать идентификаторы офферов как предложения.

### 1.2. Новый раздел «Предложения»

**Любой авторизованный сотрудник**, включая руководителя отдела, продуктовую команду и администратора, может создать предложение по развитию платформы. Неавторизованный посетитель создавать или изменять предложения не может.

Предложение описывает **бизнес-потребность/ожидаемый результат**, а не техническую работу. Отдельная сущность `proposal` с устойчивым ID, автором, инициирующим подразделением (если есть), названием, описанием, датами, статусом, историей и комментариями. Предусмотреть детальный экран и общий список с поиском и фильтрами (статус, инициатор, отдел, дата, популярность).

Процесс рассмотрения: «Новое» → «На рассмотрении» → «Принято в работу» / «Отложено» / «Отклонено» → «Запланировано» → «Реализовано». Фактические статусы и допустимые переходы уточнить и документировать, не плодить дублирующие статусы. Для отказа и откладывания обязательна причина. История решений сохраняется.

Права:

| Действие | Любой авторизованный сотрудник | Product | Admin |
|---|---|---|---|
| Создание, просмотр общих предложений, комментарии | Да | Да | Да |
| Голосование за важность | Только за отдел, в котором есть право голоса | Согласно членству | Согласно текущим правилам, с аудитом |
| Решение о принятии, отклонении, переносе | Нет | Да | Да |
| Привязка к задачам, планирование результата | Нет | Да | Да |
| Безвозвратное удаление | Нет | Нет | Да, по правилам раздела 5 |

Исключить двойные голоса одного подразделения; действующие механизмы весов и ACL использовать повторно там, где применимо. Показывать бизнесу решение продуктовой команды, прогнозируемый релиз и факт реализации без раскрытия внутренней технической информации.

**Связь предложений с задачами — многие-ко-многим:** одно предложение может реализовываться несколькими задачами, а одна задача может реализовывать несколько предложений. Не создавать автоматических дублей карточек задач. Поддержать объединение дублирующих предложений с сохранением истории и авторов. Статус «Реализовано» не должен автоматически выставляться лишь на основании даты релиза; учитывать факт завершения связанных обязательств или явное решение продукта.

## 2. Один общий «Обзор» с полноценным Гантом; отдельный планировщик Product

**Не создавать отдельный продуктовый дашборд**. «Обзор» сохраняется в основном меню и для бизнеса, и для продукта. Не переносить Гант из «Обзора» в самостоятельный обязательный раздел. Допускается полноэкранный режим того же Ганта, без дублирования данных и логики. Существующую смесь из KPI, блокировок и мини-Ганта в «Обзоре» переработать: основная функция — визуально показать, какие релизы и изменения планируются, где они находятся по этапам и когда будут выкладки. Вспомогательные бизнес-показатели оставить компактными и полезными.

Продуктовая команда должна иметь **отдельный рабочий планировщик** со всеми своими задачами (в том числе скрытыми), управлением очередью, спринтами, часами команд, бюджетом и приоритетами. Не путать это с общей визуализацией в «Обзоре». При этом следует проверить текущую двойную модель «старые плановые периоды + спринты» и подготовить переход к единой спринтовой логике; если нужна миграция или продуктовые решения, оформить её отдельно и не делать молча.

### 2.1. Внешний вид Ганта — референс GanttPRO

Именно **табличная диаграмма**, а не набор карточек с полосками:

- Слева фиксированная таблица: **Задача (ID и название) / Ответственный / Статус / Теги**.
- Справа единая горизонтальная временная шкала с полосами этапов на тех же строках; строгое выравнивание строк при скролле и раскрытии групп.
- Иерархия, раскрытие/сворачивание групп, сворачивание всех/разворачивание всех.
- Вертикальная линия «Сегодня», различимые выходные/границы недель, подписи месяцев и недель, отдельные маркеры выкладки.
- **Масштаб по умолчанию — неделя**, полосы рассчитываются по реальным календарным датам; горизонтальный скролл вправо/влево, фиксированные колонки слева.
- **Горизонт при открытии: текущий релиз + два ближайших последующих**, не обрезать более позднюю историю/планы при прокрутке.
- Фильтры по типу, статусу, ответственному и тегу, если они не перегружают экран. Клик по строке открывает карточку в пределах разрешённых данных.
- На диаграмме строки релизов, вложенных спринтов, а затем задач. Для типов работ предусмотреть группировку **«Баги», «Доработки», «Релиз»**. Название «Релиз» как тип строки означает *плановую релизную работу* (`planned`), а не ещё одну сущность релиза; различать её от строки-группы «Релиз №…». Точное текстовое имя группы можно уточнить в интерфейсе («Релизные задачи» для устранения двусмысленности). Баги и оперативные доработки показывать согласно их существующим привязкам к спринтам, но не превращать автоматически в утверждённые обязательства релиза.
- Если у задачи нет спринта либо надёжных дат, не рисовать выдуманные календарные интервалы; показать задачу в соответствующем списке/планировщике, а в общем Ганте — только при наличии оснований для отображения.

### 2.2. Цветные этапы **на каждой задаче**

**Ключевое требование:** разноцветные сегменты находятся **на индивидуальной полосе каждой задачи**, а не только на строке спринта. Гант должен отвечать на вопрос «На каком этапе разработки находится конкретная задача?».

Минимально различать разработку, тестирование и производственную выкладку; проработку показывать отдельным цветом **только если существуют достоверные данные о её датах**. Цвет означает этап, а не уникальную раскраску задачи. Дату production показывать контрольной точкой, а не искусственно растягивать «выкладку» на целую неделю.

**Базовый план этапов рассчитывается автоматически по спринту**, без ручного заполнения дат для каждой задачи:

- Разработка: `sprint.start_date` → `sprint.end_date`.
- Тестирование: `sprint.testing_start` → `sprint.production_due`, если это допустимая последовательность дат.
- Выкладка: `sprint.production_due` как предельная плановая дата/маркер.
- При наличии достоверных индивидуальных ограничений/дат задачи учитывать их по заранее описанному правилу, не генерировать ложные сроки.

В момент первого утверждения/назначения хранить **неизменяемый исходный план (baseline)** этапов задачи. Изменение расписания спринта впоследствии может пересчитывать прогноз, но **не должно затирать baseline**. Если необходим пересмотр согласованного плана — хранить отдельную историю ревизий.

### 2.3. Факт, опережение и задержки

Обычному пользователю **не нужно вручную размечать все даты этапов**. Он меняет текущий этап или подтверждает его завершение (система может использовать существующее поле `stage_id` после настройки соответствий этапов). Время изменения фиксируется как фактический переход, с возможностью корректировать фактическую дату уполномоченным пользователем и с аудитом. При необходимости Product корректирует прогноз задержки или досрочного завершения с причиной; это не изменение исторического baseline.

На Ганте явно различать:

1. Исходный план — светлая/контурная полоса.
2. Подтверждённый факт — насыщенная полоса с фактическими датами.
3. Текущий прогноз незавершённой части — отдельное визуальное состояние.
4. Опережение/задержку относительно baseline — цветовое или знаковое выделение плюс числовое отклонение в подсказке.

**Прошедшая по календарю дата не означает, что этап фактически завершён.** Не отмечать разработку и тестирование выполненными автоматически только потому, что наступил следующий день. Нужен подтверждённый переход этапа или другое явное событие. При отсутствии факта показывать «нет подтверждения»/риск просрочки, а не выдуманный прогресс. При досрочном прохождении этапа запланированная граница остаётся видимой; при задержке показывать продолжение/прогноз после неё. Статус задачи и этап разработки различать концептуально: один не должен слепо заменять другой.

### 2.4. Общие данные и видимость

И бизнес, и Product видят **один и тот же общий Гант и одну публичную для сотрудников картину планов**. Бизнес не видит внутренние задачи Product, приватные заметки, внутренние оценки, бюджет и технические процессы. Продуктовая команда смотрит закрытую информацию в отдельном планировщике. Серверные права должны действовать на строки, маркеры, счётчики, прогресс и API-ответы. Видимость данных на общем Ганте определяется публикацией/правилами общего планирования, а не только ролью просмотрщика. Внутренний планировщик и общая диаграмма могут быть построены на одной библиотеке визуализации, но иметь разные наборы данных.

## 3. Внешние ссылки задачи — ручное хранение, импорт, экспорт

В каждой карточке задачи создать отдельный блок **«Внешние ссылки»**. Типы: Bitrix24, Jira, Документация, Другое. Для каждой ссылки хранить URL, тип, необязательное понятное название, источник/происхождение, дату обновления. Разрешить несколько ссылок одного типа; ссылки открывать в новой вкладке. Проверять протокол `https://` или `http://`, экранировать/валидировать адреса; не исполнять содержимое ссылок.

**Интеграций с Jira, Bitrix24 и Confluence НЕ ДЕЛАТЬ:** не обращаться к их API, не читать документы, описания или статусы, не запрашивать OAuth, токены или технические учётные записи. Это только внешние URL.

### Импорт ссылок

- В настройке источника Google Sheets / CSV добавить соответствие произвольных колонок типам URL (Bitrix24/Jira/Документация/Другое). Например, колонка «задача в jira» попадает в ссылку Jira, а не только в описание задачи.
- Если в колонке содержится несколько URL — поддержать их разбор; одинаковые URL не дублировать.
- Учитывать URL, встречающиеся в текстовых ячейках; при необходимости извлекать адрес гиперссылки, скрытый за отображаемым текстом в Google Sheets **через API самой Google Sheets**, без обращения к Jira/Confluence. Для CSV доступны лишь реально выгруженные текстовые значения.
- Существующие ссылки, вручную добавленные в карточку, не затирать импортом. Ссылки источника обновлять идемпотентно; при конфликте ручного изменения и импорта — предпросмотр и выбор действия, а не молчаливая перезапись. Пустая ячейка не должна по умолчанию удалять вручную созданные ссылки.
- При каждом импорте показать предпросмотр: сколько ссылок добавится, изменится, не распознаётся, затронет конфликтные записи. При невалидном URL показать понятную ошибку строки.
- Не ломать существующие источники TaskFlow, багов и оперативных доработок. Отдельно проверить, как теперь формируется устойчивый ID задач при изменении их названия/исполнителя.

### Экспорт ссылок

Все внешние ссылки доступны в конструкторе экспорта с учётом прав: как отдельные поля типов и как универсальное поле «Все ссылки». Предусмотреть несколько адресов одного типа: либо дополнительные колонки, либо согласованный формат многострочной ячейки. Схему раскрыть в предпросмотре.

## 4. Конструктор экспорта — новая функциональность; детальную UX-схему согласовать отдельно

Сегодня экспорт ограничен 12 жёстко заданными колонками TaskFlow. Новый механизм должен позволять выбрать необходимые данные из карточек, настроить структуру отчёта и переиспользовать настройки.

**Согласованный минимум:**

- Отдельный удобный интерфейс конструктора, не только текущий небольшой диалог.
- Доступ ко всем допустимым для роли существующим полям задачи: ID, название, описание, тип, статус, этап, инициатор, автор, ответственный, категории/теги, сроки (baseline/текущий/факт), спринт, релиз, приоритеты, оценки по каждой команде, суммарные плановые/фактические часы, связанные предложения и внешние ссылки. Недоступные по правам поля даже не передавать клиенту.
- Выбор, порядок и названия колонок; фильтры и сортировка; **двойная группировка** (например, по спринту → ответственному или дате → задаче/типу).
- Предпросмотр реальных данных и структуры итогового файла до выгрузки; сохранение шаблонов пользователя (при доступности схемы прав — общие шаблоны отдельно).
- Excel `.xlsx` с понятной детализацией и при необходимости сводкой/группами. Google Sheets — в согласованном табличном формате, без повреждения других вкладок.
- **Существующий экспорт «TaskFlow — 12 колонок» оставить как отдельный обратносовместимый шаблон** с тем же порядком и семантикой, не ломать действующий обмен данными.
- Все агрегаты и выгрузки проверяют видимость на сервере. Скрытые задачи и приватные поля запрещено экспортировать в общее внешнее хранилище без соответствующих прав и явного подтверждения. Отдельно предусмотреть предупреждение о доступе читателей Google-таблицы.

**Не считать окончательно утверждёнными:** точный интерфейс конструктора, формы группировки строк Excel, механизм общих шаблонов и макет Google-листа. Эти детали будем обсуждать отдельно. Сначала представить 2–3 конкретных варианта и рекомендовать один; без решения владельца не кодировать жёсткую спорную UX-схему.

## 5. Полное удаление записей администратором

Администратору нужна возможность полностью удалять ошибочные, тестовые и мешающие записи. Предусмотреть отдельное «Архивировать/скрыть» и **«Удалить навсегда»**. Безвозвратное удаление — только admin, с повторным подтверждением, вводом ключа/ID объекта и предпросмотром последствий.

Объекты минимум: задачи, предложения, эпики; остальные справочники, пользователей, релизы и импортные объекты исследовать отдельно из-за связей/исторических ограничений. Не добавлять массовое удаление без отдельного утверждения.

Перед удалением показывать связанные задачи, комментарии, оценки, приоритеты/голоса, релизы, спринты, ссылки, историю импорта, последствия для метрик. Физическое удаление выполнять транзакционно и без битых ссылок; аудит события удаления должен переживать удаление самой сущности и содержать минимум данных, необходимых для разбирательства (без утечки приватных заметок). Перед массовыми или разрушительными операциями предусмотреть восстановимую резервную копию.

**Критично:** ранее удалённая импортированная запись не должна автоматически появляться вновь при следующей синхронизации. Предусмотреть tombstone/запрет повторного создания либо другой управляемый механизм с возможностью осознанно восстановить импорт.

## 6. Планировщик Product и техническая совместимость

Планировщик продуктовой команды — **отдельный от общего «Обзора» рабочий раздел**. Он должен позволять управлять задачами (включая внутренние), согласовывать приоритеты, планировать размещение в спринтах, контролировать ёмкость команд и бюджет.

Поскольку в текущей базе одновременно есть старые `capacity_periods` и новые `sprints`, проанализировать фактическое использование каждого и предложить безопасный вариант унификации. **Не мигрировать данные и не отключать старый механизм без отдельного плана и одобрения**, но обеспечить, чтобы вновь реализованный Гант и расчёт этапов брали даты именно из актуальных спринтов и не смешивали их со старыми периодами.

При изменении расписания спринта, переносе задачи, закрытии спринта, завершении или объединении задач должны корректно работать обновление прогноза, сохранение baseline, проверки связанных релизов, пересчёт доступных часов и история изменений. Если существующие бизнес-правила не позволяют конкретный сценарий, показать предупреждение и запросить отдельное решение, не обходить ограничения API.

## 7. Отдельный список дальнейших улучшений — НЕ реализовывать без согласования

Эти идеи получены из анализа текущей реализации и не являются утверждённой частью текущего пакета:

1. **Метрика выполнения обязательств спринта:** сохранять состав на старте, считать добавленные после старта, перенесённые, завершённые в срок и долю выполненного.
2. **Сценарное планирование «что если»:** предложения бизнеса, расчёт влияния на загрузку и бюджет до утверждения Product.
3. **Удобство бэклога:** настраиваемые колонки (исполнитель, спринт, дедлайн), сохранённые фильтры и представления.
4. **Исправление аналитики переносов:** учитывать перенос фактических дедлайнов, а не только статусы «отложено/отменено».
5. **Стабильная идентификация TaskFlow:** существующий hash названия+исполнителя может меняться при переименовании/переназначении; предложить стабильный ID и миграцию.
6. **План/факт бюджета:** раздельный учёт прогноза, реальных часов команд и отклонений в рублях.
7. **Технические проверки:** CI на PR, типизация, автотесты, миграционные и post-deploy smoke-тесты, резервное копирование D1.
8. **Мелкая правка:** поле месячного лимита нельзя очистить через UI при наличии API-поддержки `null`; исправить отдельным небольшим PR после проверки.

В этих пунктах допустим аналитический отчёт/предложение, но не дополнительная самовольная разработка.

## 8. Обязательные тесты и критерии приёмки

### Предложения
- Авторизованный представитель любого отдела успешно создаёт предложение; анонимный посетитель — не может.
- Сотрудник не голосует за чужое подразделение; Product принимает/отклоняет с пояснением; причина и история сохраняются.
- Один запрос бизнеса связывается с несколькими задачами, одна задача — с несколькими предложениями, без потери связей при пересмотре статуса.
- Старый модуль «Офферы» отсутствует в пользовательской навигации, импорте и новых формах; данные не потеряны без согласования.

### Общий Гант
- Представители бизнеса и Product видят одну и ту же разрешённую общую диаграмму при одинаковых условиях публикации; закрытые Product-задачи не утекли через строки, счётчики или всплывающие подсказки.
- Есть текущий и два ближайших релиза, недельная шкала, горизонтальный скролл, закреплённые колонки, дерево групп, дата «Сегодня» и контрольные точки выкладки.
- Каждая запланированная задача имеет **свои** цветные этапы, автоматически основанные на датах назначенного спринта.
- После досрочного завершения этапа видны факт и исходный план; после задержки показано отклонение и сохранён исходный план; не подтверждённый этап не становится выполненным по календарю.
- Перенос задачи в другой спринт корректно пересчитывает прогноз, не затирая историю baseline. Отсутствующие даты не подменяются вымышленными.

### Ссылки и обмен данными
- Несколько URL Jira/Bitrix24/документации хранятся в карточке, редактируются и доступны в API.
- Импорт из CSV и Google Sheets создаёт правильные ссылки, извлекает Google-гиперссылки при наличии метаданных; повторный импорт не плодит дубли и не удаляет ручные ссылки.
- Во время импорта не выполняется ни одного запроса к Jira, Confluence или Bitrix24.
- Конструктор включает ссылки и другие разрешённые поля; выгрузка с двойной группировкой предсказуема; штатный шаблон TaskFlow остаётся без изменения.

### Администрирование и регрессии
- Только admin может безвозвратно удалить запись после предпросмотра последствий и подтверждения; обычные пользователи — нет.
- После удаления нет неконсистентных связей и случайного повторного создания при импорте.
- Регрессионные тесты охватывают роли/видимость, спринты, бюджет, экспорт, импорт, API-ключи. MCP-разработку Codex не нарушать.

## 9. Порядок работы Claude

1. Провести короткий gap-analysis актуальной `main` против ТЗ: что есть, чего нет, какие миграции/скрытые зависимости понадобятся. **Отдельно перечислить спорные места, не подменяя решения владельца.**
2. Предложить архитектуру и разбивку на независимые PR. Рекомендуемый порядок: модель предложений и удаление офферов → ссылки и импорт/экспорт ссылок → модель этапов и новый общий Гант → админское удаление → конструктор экспорта. Последовательность можно изменить по зависимостям, но не смешивать всё в одном огромном PR.
3. Для каждого PR: код, безопасная миграция, автоматические тесты, скриншоты интерфейса и чек-лист ручной приёмки. Сохранить обратную совместимость действующих API в пределах согласованной миграции.
4. Перед кодированием спорной логики (особенно конструктора экспорта, унификации старых плановых периодов и физического удаления связанной истории) представить варианты решения и дождаться согласования.
5. **Не делать deploy, merge, удаление реальных данных и изменение секретов** без явного нового разрешения владельца.

**Результат первого шага:** отчёт по расхождениям, техническая схема модулей, риски для текущих данных, список предлагаемых PR с оценкой сложности и первый PR только после подтверждения плана.

# Техническое задание: развитие Rafinad Product Roadmap

**Версия:** 1.0 · **Дата:** 13.10.2026 · **Статус:** согласованный набор требований с отдельно помеченными проектными допущениями.  
**Репозиторий:** https://github.com/evgeniizhirov/rafinad-products  
**База анализа:** `main`, коммит `837998427564a181ab090261cf556c874cb01993` (12.10.2026). Перед реализацией перепроверить HEAD: репозиторий может измениться.  
**Назначение:** готовое к поэтапной реализации ТЗ для Claude Code / OpenAI Codex. Без переписывания системы с нуля.

## 0. Цель и принципы

Превратить существующий задачник продуктового отдела в единую систему управления запросами, разработкой, релизными обязательствами, оперативными исправлениями, финансовыми лимитами и аналитикой. Сохранить текущие пользователи, задачи, голоса отделов, импорты, связи и историю.

**Ключевые различия, которые нельзя смешивать:**

1. **Тип работы:** плановая продуктовая задача / баг / оперативная доработка.
2. **Область видимости:** публичная / для сотрудников / черновик / отдельный признак «внутренняя задача продукта». Текущий `visibility='internal'` уже означает «доступна сотрудникам» и **не эквивалентен** новой скрытой задаче продукта.
3. **Учётный месяц:** календарный месяц для бюджета и доступности сотрудников и команд.
4. **Спринт:** 14 календарных дней разработки, среда–вторник; возможна справочная привязка бага.
5. **Релиз:** обещанный бизнесу функционал в цикле из двух спринтов, завершается после тестирования и выкладки второго спринта. Промежуточная выкладка после первого спринта — не отдельный релиз.
6. **Плановый состав:** только предварительно оценённые плановые задачи. Баги и оперативные исправления видимы в работе, но не выбираются планировщиком и не увеличивают расчётный бюджет.
7. **Дата окончания разработки ≠ дата выкладки на прод ≠ факт исполнения релизной цели.**

### Что уже существует (не переписывать)

Стек: React 19 + TypeScript + esbuild, API в Cloudflare Workers, Cloudflare D1, cookie-сессии, роли `department_lead` / `product` / `admin`, маршруты `/api/features`, `/api/priorities`, `/api/planning`, `/api/releases`, `/api/overview`, `/api/import`. Имеются аудит, контроль версий записей, импорт из Google Sheets/CSV и механизм ручного preview/apply. Google Sheets на момент анализа поддерживается **только для чтения** (`worker/lib/google.ts`, scope `spreadsheets.readonly`). Текущие таблицы `capacity_periods`, `team_capacities`, `features.period_id`, `releases`, `release_features`, `department_votes` используются действующим MVP.

Семантика статусов задана отдельно от названий: `new`, `analysis`, `ready`, `planned`, `in_progress`, `blocked`, `postponed`, `done`, `cancelled`, `active`. Отчёты и автоматизацию строить по **семантике**, не по текстовому названию статуса. В существующем `worker/routes/priorities.ts` уже проверяется членство в отделе, а администратор вправе изменить чужую оценку только с причиной; пункт №4 — проверка и тесты, а не безусловная перепись.

## 1. Общие требования к качеству

- Пошаговые D1-миграции без удаления данных и без разрушения старых маршрутов; новые свойства обратносуместимы, старым записям назначаются безопасные значения по умолчанию.
- Единая проверка прав **на сервере** для списков, детальных карточек, поиска, отчётов, экспорта, зависимостей, подсчётов и API-ключей. Проверка только в UI недостаточна.
- Все мутации сохраняют `created_by`/`updated_by`, журнал аудита и оптимистическую блокировку там, где она уже предусмотрена. Импорт не должен незаметно перетирать вручную отредактированное.
- Валидировать JSON и ссылки на объекты, соблюдать лимиты выборок, не возвращать секреты, не раскрывать скрытые задачи даже через агрегаты, названия связей, историю и ошибки.
- Функциональные флаги и постепенный выпуск крупных изменений; бэкап D1 перед применением производственных миграций.
- Деплой на прод — только после ревью PR и отдельного применения миграций: текущая Workers Builds-сборка автоматически миграции D1 не запускает.
- Тесты на границы дат/прав, без ложных утверждений о том, что тесты успешно прошли, если они не запускались.
- Рабочая документация и API-контракт после каждого этапа; интерфейс на русском.

## 2. Реестр функциональных требований

### FR-01. Персональные API-ключи для Claude Code, Codex и интеграций

**Цель:** внешние агенты создают и читают задачи от имени реального пользователя без передачи его пароля ИИ.

**Функции:**
- Пользователь управляет своими ключами: создать, назвать, задать разрешения, срок действия, отозвать; администратор видит метаданные и может принудительно отозвать.
- Ключ показывается **один раз** при создании; в БД хранится только криптографический хэш с идентификатором/префиксом для поиска и отзыва, не открытый секрет. Не логировать значение `Authorization`.
- Аутентификация `Authorization: Bearer <token>` на существующих API или через единый middleware. API-ключ привязан к пользователю; после блокировки пользователя, отзыва или истечения срока ключ не работает.
- Scopes как минимум `tasks:read`, `tasks:create`, `tasks:update`, `priorities:write-own`, `exports:read`; потенциальные дополнительные разрешения задаются только по необходимости. Эффективные права = пересечение scope ключа и актуальных RBAC/принадлежности пользователя к отделам.
- Один ключ не даёт права администратора автоматически. Запрещён обход запрета на чужие приоритеты или на просмотр внутренних задач.
- Аудит действий API-ключа: актор, ID ключа, операция, время, результат; ограничение частоты; ротация/отзыв; экран последнего использования.
- Для первого подключения дать документацию с примером авторизации, создания и чтения карточки, но без реальных секретов.

**Критерии:** ключ пользователя `department_lead` не может вызвать `POST /api/features`, пока роль не позволяет создание; ключ `product` с `tasks:create` может; отзыв или деактивация действует немедленно; скрытая карточка не читается ключом другого отдела.

### FR-02. Внутренние (скрытые) задачи продуктового отдела

**Цель:** вести внутреннюю работу Product без раскрытия другим отделам и без включения в общие планы поставки.

**Функции:**
- В карточке при создании/редактировании переключатель **«Внутренняя задача продукта»**; отдельное структурное поле `is_product_internal` (или эквивалент). Не переиспользовать существующее `visibility='internal'`.
- Читать, создавать и редактировать такие задачи могут `product`/`admin` по существующим ограничениям. `department_lead` и неавторизованные — не видят вообще.
- Исключить из общего бэклога, открытых списков для неуполномоченных, общих приоритетов, общего Ганта, публичных релизов и их состава, зависимостей и метрик. Для Product добавить отдельный фильтр/раздел; Product видит задачи и может работать со статусом, ответственным, датами, комментариями.
- Разрешить перевод из скрытой в общую с сохранением истории и требованием подтверждения при возможной публикации.
- Внутренние трудозатраты Product **не должны автоматически превращаться в публичные записи планировщика**. Возможность учитывать агрегированную нагрузку без раскрытия деталей — отдельная настройка, по умолчанию исключить из общего планового состава и публичных агрегатов.
- Доступ к выгрузке и API определяется теми же правами; наличие `public` у прочих полей не отменяет скрытость.

**Критерии:** обычный сотрудник не получает карточку ни через `/api/features`, ни прямым запросом по ID, ни через граф, релизы, поиск, overview, выгрузку или статистику.

### FR-03. Новый главный дашборд

**Зафиксированный пользователем порядок блоков (строго):**

1. Существующая **верхняя сводка по задачам** — сохранить полезные KPI и кликабельность.
2. **Диаграмма Ганта на всю доступную ширину** — основная часть главной страницы.
3. **Цели спринта / фокусные задачи** — обязательные к поставке задачи ближайшего релиза.
4. **Блокирующие задачи** — от кого из бизнеса ожидаем вводные, согласования или решение, что блокируется и как долго.
5. **Ближайшие релизы** — компактная таблица/список с датами и ожидаемым функционалом.

**Убрать блок загруженности команд с главной**; доступность и бюджет перенести в отдельный раздел ресурсов/планирования.

**Гант:**
- Показывать только задачи, которые **реально в работе**, включая продуктовую проработку и разработку (семантика `analysis` и `in_progress`, плюс явно определённые активные этапы), **и у которых есть дата планового завершения**. Без даты завершения не показывать. `planned`/`new` без фактической работы не включать.
- Показывать плановые задачи, а также баги/оперативные доработки, отвечающие этим условиям; внутренние задачи Product исключить из общей диаграммы.
- Дата окончания на Ганте — срок фактической работы/исправления, не автоматически приравнивать к дате выпуска в прод. Для полосы использовать указанные `planned_start`/`started_at`; при неизвестной дате старта не выдумывать её: допустима визуализация контрольной точки дедлайна.
- Визуально различать типы работы, этапы, просроченные сроки, кликабельные карточки; фильтры по ответственному, команде, релизу/спринту, периоду просмотра.

**Фокус:**
- Добавить в обычные релизные задачи признак **«Фокусная задача»** и связь с целевым релизом. Это задачи, выполнение которых является обязательством перед бизнесом. Могут ещё не быть в работе, поэтому их список **не зависит от Ганта**.
- Для крупных эпиков предусмотреть отображение цели релиза и связанных фич из обоих спринтов без двойного подсчёта. Список показывает цель, её статус, обещанную дату, готовность дочерних элементов.

**Блокеры:**
- Использовать существующие связи `blocks` и семантику `blocked`, дополнить понятным бизнес-контекстом: что ожидается, кто/какое подразделение должен предоставить ответ, с какого момента, что разблокируется.
- Не ограничиваться чисто техническими зависимостями. Не разглашать названия скрытых задач через описания и ссылки.

**Релизы:** показывать обязательства полного релиза и обе промежуточные даты выкладки, без ошибочного представления каждого спринта как отдельного релиза.

### FR-04. Голосование только за собственный отдел: аудит прав

**Факт кода:** `perms.voteFor(user, departmentId)` проверяет `departmentIds`, `perms.overrideVote` только для `admin`, с обязательной причиной и журналом. UI-компонент `VoteControl` делает чужие оценки некликабельными для обычных пользователей.

**Задача:** выполнить серверные интеграционные и UI-тесты для пользователя одного отдела, нескольких отделов, администратора, пользователя без отделов, исключённого из отдела, прямого HTTP-запроса и API-ключа. Убедиться в немедленном отзыве прав при смене членства. Если найден дефект — точечно исправить.

**Критерий:** аналитик может голосовать только за аналитику, финансист только за финансы; член двух отделов — за оба; админ по чужому отделу требует причину, действие фиксируется в аудите.

### FR-05. Бюджетирование по месяцам и версии ставок команд

**Две независимые границы:**
- **Финансы и ресурсная доступность:** календарный месяц (с 1-го по последнее число месяца). Бюджетный лимит в RUB и гарантированные часы каждого сотрудника по команде за месяц; доступность команды = сумма подтверждённых часов её участников за месяц (с учётом корректировок при необходимости).
- **Исполнение:** двухнедельные спринты, которые могут пересекать границу месяца; это не бюджетные периоды.

**Ставки:**
- В администрировании редактируется ставка RUB/час каждой `resource_team`, признак `include_in_budget` и начальный спринт вступления в силу. Изменения действуют с выбранного спринта и далее, пока нет новой редакции. История неизменяема; завершённые спринты и сохранённые исторические расчёты не пересчитываются.
- Первоначально: Backend=2200, Frontend=2200, QA=2200, DevOps=2200 ₽/ч; Product и Design `include_in_budget=false`, ставка 0 для расчёта; при этом их часы считаются в доступности.
- Стоимость плановой задачи = сумма оценочных часов платных команд × ставка этих команд, действующая для назначенного спринта/участка работы.
- Бюджетный лимит задаётся на **месяц** отдельно от ставки и от количества часов.
- Планировщик проверяет обе независимые группы ограничений: месячные часы команд и месячный бюджет; при превышении предупреждает, ручное подтверждение превышения с причиной и записью аудита. Утверждённые составы не изменяются автоматически после пересчёта.
- Часы неопределённой команды ≠ 0 часов: стоимость отмечается как неполная/неоценённая; явный 0 означает отсутствие работ.
- Баги и оперативные доработки **не участвуют в плановом бюджете и доступности**. Можно хранить их факт трудозатрат постфактум отдельно для аналитики.

**Месяц × спринт (обязательная аналитическая модель):** спринт может проходить через два месяца. Прогнозные часы нужно распределять на месяцы по известным датам работ/оценкам; при отсутствии дневной разбивки рекомендуется равномерное распределение по рабочим дням планового интервала, с явной маркировкой «прогноз». Никогда не списывать автоматически все часы в месяц даты выкладки на прод. Метод распределения сделать отдельно протестированной конфигурацией. Факт отражать по датам реальных работ, когда он доступен.

**Критерии:** изменение Backend-ставки с будущего спринта не меняет закрытые периоды; два спринта могут потреблять бюджет одного месяца; спринт через 31 октября правильно разбивает нагрузку между месяцами; Product/Design не увеличивают денежную сумму.

### FR-06. Месячные учётные периоды, спринты и релизы

**Правила календаря — подтверждены:**

- Каждый спринт — **14 календарных дней**, начинается в **среду**, заканчивается во **вторник включительно**.
- В одном релизе **два последовательных спринта**.
- На следующий день после конца спринта начинается тестирование результата. **Крайний срок выкладки на прод** — четверг следующей недели, то есть **через 9 календарных дней после вторника окончания спринта**.
- Пока тестируется предыдущий, следующий спринт уже идёт.
- После спринта №1 — промежуточная выкладка части функционала, после спринта №2 — финальная поставка обязательств релиза.

**Эталон — релиз №8 (2026):**

| Событие | Спринт 8.1 | Спринт 8.2 |
|---|---|---|
| Разработка с | 07.10.2026, среда | 21.10.2026, среда |
| Разработка по | 20.10.2026, вторник | 03.11.2026, вторник |
| Тестирование начинается | 21.10.2026 | 04.11.2026 |
| Крайний срок выкладки | 29.10.2026, четверг | 12.11.2026, четверг |

**Новые сущности:** `sprints` (номер релиза + ordinal 1/2, start, end, testing_start, production_due, lifecycle), `release_sprints`; месячные `accounting_months`/`capacity_months` или аккуратное переиспользование `capacity_periods` с явной семантикой «календарный месяц». Нельзя разрушить старые `features.period_id` и связанные версии/планировщик. Важен отдельный явный `features.sprint_id` для плановой задачи; `release_id` или связь через текущую `release_features` остаётся самостоятельной.

**Плановый период в карточке:** существующее поле пользователь воспринимает как срок появления задачи на проде. После расширения карточка должна явно показывать **Релиз → Спринт → Плановая дата выкладки**, автоподставлять `production_due` выбранного спринта. Не смешивать это поле с месячной ёмкостью. Миграция должна сохранять прежние периодные назначения, в т. ч. неразрешённые/исторические, и явно помечать требующие сопоставления.

**Генератор:** кнопка «Создать следующие периоды» с предпросмотром и безопасная автогенерация (допустимо обе опции) из опорной даты 07.10.2026, релиз 8. Уникальность, идемпотентность, запрет дублей, проверка пересечений и опциональное редактирование исключений с аудитом. Создавать месяцы независимо от спринтов. Не передвигать задачи при генерации.

**Состав и декомпозиция:**
- Крупное релизное обязательство/эпик может состоять из нескольких фич, распределённых между обоими спринтами.
- Каждая плановая фича связывается со своим спринтом; срок выкладки по умолчанию берётся из спринта.
- Промежуточная выкладка не закрывает релиз целиком, если обязательные элементы ещё не поставлены.
- Если задача переносится из 8.1 в 8.2 — фиксировать историю переноса и обновить плановую дату выкладки, не изменяя реальную фактическую дату.
- Один спринт для одной фичи в плане на текущий момент, эпик может охватывать два спринта.
- Баг может быть связан со спринтом **только справочно** и не включается в утверждённый набор задач и автоматические рекомендации.

**Критерий:** генерация следующего цикла выдаёт точные даты; повторный вызов не создаёт дублей; месяцы октябрь/ноябрь не совпадают искусственно со спринтами.

### FR-07. Баги и оперативные доработки: отдельный поток

**Классификация:**
- `bug` — реализация не соответствует корректному ожидаемому поведению/требованиям, вина разработки.
- `operational_improvement` — реализация корректна по ТЗ, но результат не отвечает потребности из-за продуктовой недоработки, непредвиденных ограничений и т. п.
- `planned` — плановая задача. Баг и оперативная доработка имеют **одинаковый процесс**, различаются классификацией для аналитики.

**Поля:** название, описание, тип, дата поступления (автоматически), срочность (не продуктовый межотдельный голос), ответственный (при наличии), состояние `не решено / в работе / решено`, плановая дата устранения (опционально), фактическая дата устранения, при необходимости справочный `sprint_id`, фактические часы после завершения (опционально, отдельный учёт).

**Поток:**
- Не требуют предварительных оценок часов и не включаются в ресурсную/денежную ёмкость планировщика.
- Не участвуют в компоновке релизного/спринтового обязательного состава, автоматическом подборе задач, приоритизации бизнес-отделов или расчёте планового бюджета.
- На главном Ганте отображаются, если действительно выполняются и имеют дату предполагаемого завершения. Без даты не показывать.
- Справочная привязка к спринту возможна для ответа «в ходе какого спринта исправляем», **но не означает включения в спринтовый план**.
- Если обнаружено, что работа существенная и заранее оценивается, её следует оформить/конвертировать в обычную плановую задачу с релизом и оценками; не учитывать одновременно как баг и плановый элемент.

**Критерии:** баг со сроком и статусом «в работе» виден в Ганте, но отсутствует в подборе задач на спринт, сумме плановых часов и бюджета; срочность видна отдельно.

### FR-08. Ручной экспорт задач (Excel и Google Sheets)

**Итоговый выбор пользователя — не автоматическая публикация всех задач.**

- На списке задач кнопка **«Экспорт»**; используются текущие фильтры: тип, статус, семантика, релиз, спринт, отдел, приоритет, ответственный, инициатор, даты, внутренние/общие (если доступно), поиск.
- Выбор направления: **скачать `.xlsx`** либо **выгрузить в Google Sheets** в заранее настроенный документ, вкладка с точным названием **`Import`**.
- Экспортируются **все** соответствующие фильтрам задачи, а не только первая страница таблицы.
- Текущий пользователь получает **только разрешённые ему задачи и разрешённые поля**. Сервер повторно применяет фильтры и ACL; нельзя передавать `include_hidden=true`, чтобы обойти ограничения.
- Одна строка = одна задача; одинаковая схема колонок в XLSX и Google, стабильный `RF-ID`, тип, название, описание (при доступе), семантический/видимый статус, инициатор, автор создания, дата, ответственный, приоритет, даты, релиз/спринт и т. п.; пустые допустимы.
- Текущие защищённые/внутренние задачи доступны для экспорта только Product/Admin, если имеют к ним доступ.
- Google Sheets: запись только в **конфигурируемый администратором разрешённый документ и вкладку `Import`**, другие листы не трогать. Перед заменой содержимого вкладки подтверждать пользователю, что все читатели документа Google увидят экспортированное; проверять отдельное право на Google-экспорт, логировать кто/когда/что выгрузил. Предусмотреть защиту от гонки двух выгрузок и частичного перезаписывания; ошибка не должна испортить соседние вкладки.
- Никакой автоматической синхронизации/расписания на данном этапе; никаких циклов обратного импорта.
- Текущий сервисный аккаунт работает только в `spreadsheets.readonly`: для экспорта в Google придётся добавить отдельный write scope/клиент, предоставить именно таблице право **«Редактор»**, хранить JSON только в рабочем секрете Cloudflare, никогда не в Builds, GitHub и логах. Уже созданный JSON может быть переиспользован; новый не нужен.

**Критерии:** сотрудник не может экспортировать скрытую продуктовую задачу, даже зная её ID; экспорт 700 строк не обрезается до UI-страницы; формат совпадает; Google обновляет только `Import`.

### FR-10. Инициатор задачи — три формы

**Отдельно от `created_by`, `author_name`, `assignee_name`.**

Поле **«Инициатор»** в создании/редактировании и просмотре задачи:

1. `free_text` — ручной ввод «Фамилия Имя» для человека без учётной записи;
2. `user` — ссылка на пользователя Roadmap;
3. `department` — ссылка на отдел из справочника.

Хранить тип, ID при ссылке, человекочитаемый snapshot имени на случай переименования/деактивации. Поле необязательное для исторических задач, редактируемое с историей. Фильтрация и группировка по инициатору, экспорт. При импорте поддержать сопоставление текстового поля с отделом/пользователем там, где это однозначно, иначе свободный текст. Не приравнивать автора HTTP-запроса или обладателя API-ключа к инициатору без явного выбора.

**Критерий:** внешний пользователь, отдел и ручное ФИО корректно отображаются и не теряются после смены профиля; пустое поле не ломает старые данные.

### FR-11. Аналитика и отчётность

Создать отдельный раздел **«Аналитика»**. Не загружать главный дашборд тяжёлыми отчётами. Показатели с фильтрами по периоду, источнику, команде/отделу, типу, инициатору, автору постановки, исполнителю, релизу, спринту. Каждый счётчик кликабелен и ведёт к исходной выборке задач; экспортировать отчёты с соблюдением ACL.

**Блок A — объём и операционная эффективность:**
- Поступило, открыто, в работе, завершено, отменено, отложено, просрочено, заблокировано; новые баги, активные баги, устранённые баги, оперативные доработки.
- **Своевременность**: доля завершённых задач с фактической датой `<=` зафиксированного обязательного/базового срока. Не подменять исходный срок последней перенесённой датой. Показать количество задач без исходного срока отдельно.
- **Время цикла**: от начала работы до `done`, отдельно медиана/перцентили для багов и обычных задач, только при достаточности timestamps.
- **Блокировки**: количество, причина, бизнес-владелец, накопленная длительность, просроченные ожидания.
- **Релизная дисциплина**: доля обязательств, поставленных до обещанной даты продакшена; отдельно компоненты промежуточной выкладки.

**Блок B — кто ставит задачи:**
- Рейтинг и динамика по **автору карточки** (`created_by`) и **инициатору** (FR-10) — два независимых разреза.
- Разбивка по отделу, типу, семантическому состоянию и периоду; различать действия людей и ИИ-агентов от имени пользователя (ID ключа в аудите).

**Блок C — востребованность («полезность») идей:**
- Доля задач с высоким **взвешенным межотдельным приоритетом**; порог — настраиваемая величина (предлагаемый старт `>=4` из 5, но должен подтверждаться Product; отдельная колонка «строго 5»).
- Конверсия поступивших задач в `planned`, `in_progress`, `done`, и доля ушедших в `postponed`/`cancelled` по **семантическим кодам**, не по именам.
- «Востребованные реализованные» — задачи, получившие высокий приоритет и реально завершённые, **не проходившие через отложение/отмену**, если история статусов достоверно доступна. Обязательно отдельно показывать **ещё не решённые** задачи, чтобы не штрафовать недавно поставленные.
- По авторам и инициаторам можно сравнивать качество постановки, не называя показатель прямым доказательством бизнес-ROI: это показатель **спроса и доведения до реализации**.
- Исторические переходы статусов, приоритетов и переносы сроков: хранить с момента внедрения; исторические данные, которых нет, помечать `нет истории/недостаточно данных`, а не выдумывать.
- Разграничение доступа распространяется на агрегаты и выдачу underlying строк (не допускается утечка количества скрытых задач).

**Критерии:** смена отображаемого названия статуса не меняет расчёты; инициатор и создатель отличаются в отчёте; пустая история не интерпретируется как «никогда не откладывалась».

## 3. Предлагаемая модель данных и контракты (проектное решение, доработать после обследования)

**Это ориентир реализации, не жёсткое требование буквально назвать поля так же.** Разработчик проверяет существующую D1-схему и предпочитает аддитивные миграции.

| Объект | Поля/структуры (ориентир) | Принцип |
|---|---|---|
| `features` | `task_kind`, `is_product_internal`, `initiator_type`, `initiator_user_id`, `initiator_department_id`, `initiator_text`, `sprint_id`, `is_focus`, `planned_production_date`, `baseline_due_at`, `started_at`, `resolved_at` | миграция старых задач в `planned`, nullable новые поля |
| `sprints` | `id`, `release_id`, `ordinal`, `start_date`, `end_date`, `testing_start`, `production_due`, `status`, `closed_at` | 2 спринта на релиз, уникальность `(release_id, ordinal)` |
| месяцы | уникальный `YYYY-MM`, начало/конец месяца, лимит RUB, статус | не приравнивать к спринту |
| месячная ресурсная доступность | `month_id`, `team_id`, `user_id`/идентификатор сотрудника, подтверждённые часы | суммирование по команде; без обязательной публикации персональных данных |
| история ставок | `team_id`, `effective_sprint_id`, `rate_rub_per_hour`, `include_in_budget`, версия/актор/дата | не изменять закрытые версии |
| `api_keys` | `id`, `owner_id`, `name`, `secret_hash`, `prefix`, `scopes`, `expires_at`, `revoked_at`, `last_used_at` | ключ показывается 1 раз |
| `bug_fields` или расширение `features` | `urgency`, `planned_resolution_date`, `resolution_state`, `fact_hours`, `reference_sprint_id` | не участвует в плановом составе |
| блокеры | `blocked_feature_id`, причина, бизнес-владелец, ожидаемое действие, started_at, resolved_at | существующие `feature_relations` продолжить поддерживать |
| `export_runs` | actor, target, query/filter snapshot, count, timestamp, status | аудит без выгрузки секретов |
| история метрик | история статусов, приоритетов, обещанных сроков и событий выкладки | не выводить исторический факт из одного текущего статуса |

**Особая совместимость:** исходный `features.period_id` ссылается на `capacity_periods`; исходный `releases.planned_date` — отдельная дата. Не заменять смысл этих колонок «в лоб». Должны существовать явная миграционная карта и стратегия сохранения старых размещений.

### Предлагаемые API (ориентир, точные маршруты согласовать с текущим Router)

| Назначение | Пример |

### Запрет опасных сокращений

- Нельзя делать «внутреннюю задачу» как `visibility='internal'` — этот уровень уже читают обычные сотрудники.
- Нельзя привязывать месячный бюджет к дате выкладки всего спринта.
- Нельзя добавлять баг в состав спринта только потому, что у него указан `sprint_id`.
- Нельзя включать API-key-аутентификацию без пересечения с RBAC.
- Нельзя экспортировать данные простым копированием текущего client-side списка.
- Нельзя брать текущий статус задачи как полную историческую картину при расчёте «не была отложена».
- Нельзя записывать приватный Google JSON в GitHub, логи, конфигурационные JS-файлы или секреты сборки (только runtime Cloudflare Worker).

## 6. Обязательные команды проверки

В корне репозитория после установки зависимостей:

```bash
npm install
npm run typecheck
npm test
npm run build
```

Проверка D1-миграций на чистой и существующей локальной базе; тестирование сценариев T01–T20; тестирование доступов трёх ролей и гостя. В `README` документированы `npm run dev:node`, `npm run dev`, `npm run db:migrate:remote`. **Не применять `db:migrate:remote` и не делать `wrangler deploy` без отдельного явного разрешения владельца**; деплой не подменяет миграцию D1.

## 7. Открытые проектные решения — НЕ выдавать за согласованные требования

1. **Порог высокого приоритета** в аналитике: предлагается `>=4/5`, но конечное значение должно быть настраиваемым/согласованным.
2. **Точное распределение прогнозных часов по месяцам** при пересечении спринтом границы календарных месяцев. Предложен метод рабочих дней; нужно подтвердить его с владельцем. До решения нельзя считать «бюджет месяца» бухгалтерски точным.
3. **Источник гарантированных часов по сотрудникам:** создаются вручную в Roadmap или импортируются из другой системы; необходим UX и справочник исполнителей, возможен первый релиз с вводом команды агрегатом и последующим расширением.
4. **Состав колонок экспорта**: предложен стабильный разумный набор и настройка порядка; финально согласовать с примером таблицы.
5. **Точные заголовки и идентификаторы** двух вкладок Google-источника багов должны быть считаны из таблицы в процессе реализации; эта версия ТЗ не заявляет, что закрытая таблица просмотрена.
6. **Глубина автоматической генерации** (например, вперёд на 3 релиза и 12 месяцев) — предложение для настройки, не обязательное фиксированное значение.
7. **Назначение ответственных за бизнес-блокер** и потенциальное разграничение между отделом-инициатором и владельцем решения — выбрать UI после проектирования.
8. **Роли выгрузки в общую Google-таблицу:** возможна всем авторизованным с отдельным permission; предусмотреть админ-управление и явное подтверждение раскрытия данных читателям внешней таблицы.

## 8. Definition of Done для любого PR

- Точно обозначена входящая функциональность и что сознательно не входит.
- Миграция аддитивная, `up` идемпотентна в принятом процессе, исторические данные сохранены; описан rollback или восстановление из бэкапа.
- Новый API/DTO документирован, входные параметры проверены; не нарушен прежний клиент.
- Добавлены автоматические тесты happy-path + ACL + отрицательные/пограничные случаи.
- `typecheck`, `test`, `build` завершились успешно локально — с реальными логами, без фиктивных заявлений.
- PR содержит список затронутых файлов, инструкции по миграции/проверке и скриншоты значимых UI-изменений.
- Нет секретов и токенов в commit/diff. Рабочая конфигурация Google находится в runtime Worker Secrets.
- Никакого автоматического merge/deploy на прод без согласования владельца.

## 9. Результат всего проекта

Пользователь видит целостную панель обязательств и работ; Product умеет вести приватные задачи; команды фиксируют прогнозы, бюджет и фактическую оперативную работу; сотрудники голосуют только от своего отдела; задачи создаются внешними агентами по ограниченным ключам; данные можно безопасно импортировать и вручную выгружать; руководители получают отчёты по срокам, качеству и востребованности входящих запросов.

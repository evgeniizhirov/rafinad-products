## Конкретная работа

1. Изучи `capacity_periods`, `features.period_id`, `releases`, `release_features`, `worker/routes/planning.ts`, `worker/routes/releases.ts`, существующие UI страниц Planning и Releases и алгоритм `worker/domain/planner.ts`. До изменения опиши стратегию миграции, **не меняй семантику существующего period_id в лоб**.
2. Введи отдельные календарные месяцы для будущего бюджета/ресурсов (первое–последнее число) и спринты как два дочерних элемента релиза. Связь задача→спринт должна существовать помимо задачи→релиз. Сохранить старые назначения и выявлять те, которые невозможно автоматически сопоставить.
3. Генератор на базе опорного `release 8, sprint 1, 2026-10-07`: разработка 07–20.10, следующий 21.10–03.11; тестирование со следующей среды; прод 29.10 и 12.11. Спринт=14 дней Wed–Tue, конец prod на +9 календарных дней после окончания. Релиз=2 спринта; финальное обязательство после второго. Создание по preview→commit, повторный вызов idempotent, проверка дублей/пересечений. Старые закрытые периоды не перетирать.
4. Карточка задачи: выбор релиза, затем спринта только выбранного релиза, автопоказ даты выхода на прод. При переносе в другой спринт — новый плановый срок с историей. Разделять дату конца работы, дату prod и фактическую дату.
5. Добавить признак «Фокусная задача» для релизного обязательства; учесть цели-эпики с фичами обоих спринтов. Спринт и релиз продолжают существовать независимо от календарного месяца. Баги могут иметь справочный спринт, но **никогда** не входить в плановый состав.
6. Нужны API и UI просмотра календаря; не переписывай существующий планировщик полностью. Продумай переходный адаптер до P04 и тесты совместимости.

- Даты 8.1/8.2 абсолютно точны и проверены на пересечение месяцев.

- Старые `features.period_id` и утверждённые release_features не потеряны.
- Release/sprint/prod видны в карточке задачи и меняются корректно, focus отделён от статуса.

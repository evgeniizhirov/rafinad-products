## Конкретная работа

1. Работай только после merge P03. Проверь новые месяцы/спринты, текущие `resource_teams`, `team_capacities`, `feature_estimates`, `worker/domain/planner.ts`, `worker/routes/planning.ts`. Сначала опиши математическую модель расчёта и исторические снимки, предложи решение открытого вопроса распределения часов через границу месяца.
2. В Admin добавь ставки RUB/час для каждой команды с `include_in_budget`, версионированием от выбранного спринта. Defaults Backend/Frontend/QA/DevOps=2200, Product/Design=0 и не участвуют в рублёвых суммах; в часовой ёмкости Product/Design остаются.
3. Введи календарный месячный бюджет RUB и месячные гарантированные часы по командам, при возможности по сотрудникам с агрегацией. Отдели прогнозную и фактическую стоимость. Сделай исторический snapshot для закрытых спринтов/периодов; изменение ставки в будущем не переписывает прошлое.
4. Плановый бюджет учитывает только `planned` tasks и предоценки команд; баги/оперативные доработки игнорируются, их постфактум время можно сохранять отдельно. Отсутствующая оценка не считается 0.
5. Для спринтов через границу месяцев распределять затраты по реально известным рабочим датам, а без них — по явной прогнозной аллокации на рабочие дни, помечая результат прогнозным. Требования FR-05 отмечают выбор метода как решение на подтверждение — реализацию сделать конфигурируемой и задокументировать допущение.
6. Сравнивать помесячные бюджет и доступность в процессе автопланирования; превышения требуют причины и подтверждения в ручном режиме; состав утверждённых задач сам не меняется.
7. UI бюджета и загрузки — в разделе планирования/ресурсов, не на главном overview.

## Критерии приёмки

- Оплата Product/Design=0 при любых часах; часы остаются в доступности.
- Future rate не изменяет завершённый период.
- Одновременно проверяются месячная ёмкость и месячный RUB-лимит.
- Граница октября/ноября правильно распределяет прогнозные расходы.
- Баги/доработки не съедают плановую ёмкость или рублёвый бюджет.

## Конкретная работа

1. Проанализируй структуру `features`, существующие `visibility`, feature DTO в `worker/lib/world.ts`, маршруты `worker/routes/features.ts`, формы `client/src/features.tsx`, карточку `client/src/pages/FeatureDrawer.tsx`, импортер и поиск.
2. Аддитивной миграцией введи: тип работы `planned|bug|operational_improvement` (у старых `planned`), **отдельный** флаг `is_product_internal`, инициатор с тремя вариантами `free_text|user|department` и nullable snapshot имени. Не превращай `visibility='internal'` в «внутреннюю задачу Product».
3. Серверные create/read/update/list/search должны проверять права: Product/Admin видят свои внутренние; department_lead/guest не видят никак. Для скрытых задач исключи утечки через overview, граф, relations, релизные подборки, общий бэклог, meta/counts и export-ready DTO. Добавь регрессионные тесты на 404/403 без раскрытия существования ID.
4. UI: селектор типа работы, чекбокс «Внутренняя задача продукта», три способа указать инициатора, фильтр «Внутренние задачи» только Product/Admin. Инициатор и автор/исполнитель — разные поля.
5. Оперативные баги и доработки только получают тип на этом этапе; их полноценный процесс, urgency и импорт будет в P05. Обеспечь безопасный контракт для будущих этапов.
6. Сохрани существующие `created_by`, `author_name`, `assignee_name`, истории и текущие записи. Старый клиент работает, когда новые поля отсутствуют.

## Критерии приёмки

- Старые задачи остаются доступными и по умолчанию `planned`.
- Department_lead/guest не видят скрытые Product-задачи в любом API и агрегате.
- Product/Admin создают/редактируют/раскрывают внутреннюю задачу с историей.
- Инициатор ФИО, пользователь, отдел и пустой вариант работают, фильтруются и отображаются.
- Типы задач валидируются на сервере, старый импорт не сломан.

## Конкретная работа

1. Реализуй отдельный раздел Analytics и отдельные доменные функции расчётов/агрегаты. Читай статусную семантику из `statuses.semantic`, а не имена; используй единый ACL, те же task_kind, creator и initiator.
2. Операционная сводка: создание, поток, сроки, done/overdue/postponed/cancelled, баги, длительность решения, блокеры по бизнес-владельцу, релизные обязательства; кликабельный drill-down до исходного набора задач с теми же правами.
3. Кто ставит: отдельно `created_by` и `initiator` (user/department/free-text), динамика и распределение по типам и отделам. Действия API key относятся к владельцу ключа, а не автоматически к инициатору.
4. Востребованность: доля получивших высокий score (предложение >=4/5 configurable, отдельно score=5), из них сколько planned/in_progress/done/postponed/cancelled; отдельная конверсия «высокий приоритет и доведено до done без перехода в postponed/cancelled» **только при наличии достоверной истории**. Нельзя выдавать истории приоритетов/статусов, которых нет. Недавние и активные задачи исключать из метрики окончательных решений либо показывать отдельным знаменателем.
5. Для своевременности фиксировать первичный baseline deadline при первом обещании и историю переносов; фактические closed/prod даты не путать. В отчётах разделять случаи без baseline. Не приравнивать спрос к экономическому ROI.
6. Фильтры по датам, автору, инициатору, отделу, типу, релизу, спринту, семантике; экспорт отчётов там, где разрешено. Протестировать любой переименованный статус с прежним semantic; права на hidden aggregate.
7. Зафиксировать формулы в docs, хранение snapshots/events для будущих отчётов, производительность выборок и индексы.

## Критерии приёмки

- Метрики воспроизводятся на тестовом наборе с известными датами/переходами.
- Переименование статуса не меняет статистику.
- Разрез «автор» отличается от «инициатор».
- У истории без данных появляется метка «недостаточно данных», а не ложный 0.
- Скрытые задачи не раскрываются через сводки и drill-down.

# План реализации в Codex: зависимости, ветки, PR

**Вход:** `00_MASTER_TZ.md` (функции FR-01..FR-11), последняя сводка Claude, `main` на GitHub.  
**Выход:** небольшие независимые Pull Requests, проверенные тестами, без автоматического prod deploy.

## Основная последовательность

```text
P01: проверка ACL голосования ─────────────────────────────────┐
                                                               │
P02: общая модель задач + Product internal + инициаторы ──────┤
  │                                                            │
  ├── P03: спринты / релизы / месяцы / focus ─┐                │
  │                                           ├── P04: бюджет ─┤
  ├── P05: баги + Google import ──────────────┤                │
  │                                           ├── P06: Гант ───┤
  ├── P07: персональные API-ключи ────────────┤                │
  │                                           ├── P08: экспорт ┤
  └───────────────────────────────────────────┴── P09: отчёты ┘

             Финальный интеграционный тест, ручная приёмка, затем деплой
```

**Параллельность:** P01 можно начать до P02. P03 и P05 после P02 могут идти параллельно в разных ветках с разными владельцами; P07 независим от календаря и бюджета; P06 и P08 лучше после слияния P03/P05; P09 ближе к концу. Никогда не запускать два агента на одинаковые глобальные файлы без согласованного контракта.

## Стандартный регламент для каждого агента

1. Прочесть README, `00_MASTER_TZ.md`, relevant modules и существующие тесты; проверить `git status` и SHA `main`.
2. Создать свою `codex/*` ветку от текущего `main`. Не выполнять код в той же директории, где запущен Claude (использовать отдельный checkout / Git worktree).
3. Сначала короткий план изменений, список новых таблиц/полей и API-контракт. Если возникает конфликт с готовыми модулями — отметить его до изменения кода.
4. Реализовать **только текущий этап**, не двигаться на следующий автоматически.
5. Добавить автоматические тесты на роли, невалидные входные данные, повторные запросы, историческую совместимость; не хранить настоящие ключи Google в фикстурах.
6. Прогнать `npm run typecheck`, `npm test`, `npm run build`. Миграцию прогнать на новой и копии существующей локальной БД.
7. Открыть PR с чеклистом, конфликтами миграций и инструкциями по проверке. Не объединять, не выполнять D1 remote migrations/deploy.
8. После merge перезагрузить `main`, `git rebase main` на следующей ветке, разрешить конфликты по смыслу, повторить тесты.

## Как сэкономить токены

- В новом Codex-диалоге передавай **главное ТЗ один раз**; дальше только файл конкретного этапа и нужные факты об изменённой ветке.
- Проси прежде всего **реализацию и реальные проверки**, а не многостраничное повторное описание ТЗ.
- Если PR слишком велик (условно > 20–25 изменённых файлов), разделить по вертикали `DB+API` / `UI+tests`, с контрактом между ними.
- Для каждой функциональности сначала проверить, что уже есть в проекте; FR-04, например, содержит реализацию ACL — возможно, потребуется только тестирование.
- Приложить к PR `docs/IMPLEMENTATION_NOTES.md` или компактный отчёт с фактическими решениями, чтобы следующий агент не тратил время на восстановление контекста.

## Где заканчивается полномочие Codex

Он вправе менять исходный код в своей ветке и запускать локальные проверки. **Нельзя**: читать/выгружать личные ключи, заменять Cloudflare production secret, применять D1 remote миграции, публиковать production, удалять существующие данные или мержить PR без согласования владельца.

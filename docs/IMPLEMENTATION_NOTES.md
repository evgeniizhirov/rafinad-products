## P02 — основа модели задач (FR-02, FR-07 база, FR-10) · ветка `claude/02-task-foundation`

**Миграция `0003_task_foundation.sql`** (аддитивная), новые столбцы `features`:

| Столбец | Значение |
| --- | --- |
| `task_kind` | `planned` / `bug` / `operational_improvement`, по умолчанию `planned` |
| `is_product_internal` | 0/1 — скрытая задача Product. **Не связана** с `visibility` (`internal` = видна всем сотрудникам) |
| `initiator_type`, `initiator_user_id`, `initiator_department_id`, `initiator_name` | инициатор; `initiator_name` хранит свободный текст или снимок имени пользователя/отдела на момент выбора |

**Скрытые задачи — одно правило в `worker/lib/world.ts`:**
- `loadWorld(db, viewer, { includeInternal })` вырезает скрытые задачи и **все ссылающиеся строки**: голоса, оценки, теги, офферы, связи, релизы. Поэтому они не попадают ни в один список, счётчик, граф или агрегат — даже как плейсхолдер «скрыта».
- `includeInternal: true` действует только для product/admin и используется только в `GET /api/features` (`?internal=1|all`) и в карточке `GET /api/features/:ref`.
- Общие виды (overview, roadmap, priorities, releases, epics, offers, graph, planning) не показывают скрытые задачи никому, включая Product.
- `resolveFeature()` отдаёт 404 «Задача не найдена» всем, кроме product/admin. Это закрывает все write-маршруты (голоса, комментарии, связи, оценки, размещение).
- История карточки для не-editor отфильтровывает записи `relation_added`/`relation_removed`, где упоминается id скрытой задачи.
- `canSeeFeature(viewer, f)` — правило для одной задачи; `visibleFeatures(w, viewer, 'general'|'internal'|'all')`.
- Раскрытие (`is_product_internal` 1→0) требует `confirm_disclose: true`, иначе 409 `confirm_disclose`; изменение идёт в аудит.
- Скрыть задачу, которая входит в релиз, нельзя (400).

**Тип работы:**
- `isPlannable(f)` = `planned` и не скрытая.
- Только такие задачи участвуют в планировщике (`plannerInput`, `currentLoad`, `versions` плана), в ёмкости (`overloadFor`), в размещении по периоду (иначе 400) и в составе релиза (новые добавления — 400).
- Плановую задачу из релиза нельзя превратить в баг (400). Баг в плановую — можно.
- Баги видны в общих списках: это реальная работа. Фильтр — `?kind=bug,operational_improvement`.

**Инициатор:**
- API: `initiator: null | {type:'free_text', name} | {type:'user', user_id} | {type:'department', department_id}`.
- DTO для сотрудников: `initiator: {type, name, user_id?/department_id?, inactive?}`. Гостям поле не отдаётся.
- Фильтр `?initiator=user:<id>|department:<id>|text:<подстрока>|none`.
- `GET /api/users/directory` (product/admin) — только `id` и `name` активных пользователей, без email.

**UI:**
- Форма задачи: тип работы, «Внутренняя задача продукта», инициатор в трёх формах.
- Карточка: тип и инициатор. В списках — бейджи «Баг» / «Оперативная доработка» / «Внутренняя продукта».
- Бэклог: фильтры типа, «Внутренние задачи продукта» (только product/admin), инициатора по отделу.

**Локальные миграции:** `scripts/sqlite-d1.ts → migrate()` теперь ведёт `d1_migrations` и применяет только недостающие миграции. `npm run dev:node` обновляет существующую `.local/dev.sqlite`. Проверено на копии с 61 задачей: все получили `planned`.

**Не входит:** процесс багов (срочность, состояние, даты устранения) — P05; спринты — P03.

## P03 — спринты, релизы, месяцы, фокус (FR-06, фокус из FR-03) · ветка `claude/03-sprint-calendar`

**Миграция `0004_sprint_calendar.sql`:**
- `releases.cycle_number` — номер цикла, уникальный, если задан; у старых релизов NULL.
- `sprints` — `release_id`, `ordinal` 1/2, `code` «8.1», даты, `status` planned/active/closed; уникальность `(release_id, ordinal)` и `code`; CHECK на порядок дат.
- `accounting_months` — `month` YYYY-MM (уникальный), 1-е — последнее число, `budget_limit_rub` на будущее (P04), `status`.
- `features`:
  - `sprint_id` — для плановых задач это план спринта, для багов только справка;
  - `planned_production_date`;
  - `baseline_production_date` — первое обещание, при переносах не меняется (нужно для FR-11);
  - `is_focus`.
- Настройки: `calendar_anchor_date=2026-10-07`, `calendar_anchor_release=8`, `calendar_releases_ahead=3`, `calendar_months_ahead=12`. Администратор меняет их через `PUT /api/admin/settings`.

**Совместимость:** `capacity_periods` и `features.period_id` не тронуты, планировщик работает как раньше. Автоматического сопоставления «период → спринт» нет: такие задачи перечислены в `GET /api/calendar → unmapped` и на странице «Спринты».

**Домен `worker/domain/calendar.ts`** (чистые функции):
- `releaseCycle(anchor, n)` — спринт 14 дней ср–вт, тест с +1 дня, прод через +9 дней после конца спринта.
- `cycleOn`, `monthDates`, `addMonths`.
- `planGeneration(anchor, existing, {today, releasesAhead, monthsAhead})`:
  - окно — от опорного релиза до текущего + N вперёд, по месяцам аналогично;
  - существующие записи пропускаются, а не двигаются;
  - вручную изменённый спринт попадает в отчёт;
  - пересечение даёт конфликт, а не дубль.

**API (`worker/routes/calendar.ts`):**

| Маршрут | Доступ | Что делает |
| --- | --- | --- |
| `GET /api/calendar` | все; гости — только публичные релизы, без месяцев | релизы-циклы со спринтами, месяцы, текущий спринт, `unmapped` для product/admin |
| `GET /api/sprints`, `GET /api/sprints/:id` (id или код «8.1») | все | `features` — план, `reference` — справочные баги |
| `POST /api/calendar/generate-preview` → `{plan, plan_hash}`; `POST /api/calendar/generate {plan_hash}` | product/admin | генерация; при изменении календаря после предпросмотра — 409 `stale`; идемпотентно; уникальные индексы защищают от параллельного запуска |
| `PATCH /api/sprints/:id` | product/admin | исключение: даты/статус, причина обязательна, пересечения запрещены. Задачи, у которых срок совпадал со старым сроком выкладки спринта, и `releases.planned_date` (для спринта 2) следуют за новым сроком. `baseline` не меняется |
| `PATCH /api/features/:id/schedule {release_id?, sprint_id, planned_production_date?, version, confirm_approved_change?, reason?}` | редакторы | см. ниже |

Правила `PATCH /api/features/:id/schedule`:
- Плановая задача: спринт задаёт релиз (`release_features` синхронизируется), дата выкладки = срок спринта, если не задана явно.
- Перенос пишется в аудит как `rescheduled` (спринт `8.1 → 8.2`, новая дата).
- Изменение состава утверждённого релиза — 409 `approved` без подтверждения и причины.
- Баг или доработка: только справочный `sprint_id`; релиз — 400; дата не трогается.
- Внутренние задачи продукта: 400.

**Прочее:**
- Если задача убрана из релиза через `PUT /api/releases/:id/features`, её спринт и плановая дата сбрасываются.
- Сводка релиза дополнена: `cycle_number`, `sprints[]` (по каждому — задач/готово), `focus_count`, `focus_done`. Готовность считается по обоим спринтам: первая выкладка релиз не закрывает.
- `is_focus` допустим только для плановой общей задачи; задача, переставшая быть плановой, теряет фокус.
- Фильтры бэклога: `?sprint=<id|none>`, `?focus=1`.

**UI:**
- Раздел «Спринты» (`/calendar`): таблица релизов со спринтами и датами, месяцы, предпросмотр генерации, список несопоставленных задач.
- Карточка, вкладка «Ресурсы»: блок «Релиз, спринт и выкладка» (или «Спринт (справочно)» для багов). Во вкладке «Описание» — «Релиз → спринт», плановая выкладка и первое обещание.
- Форма: чекбокс «Фокусная задача релиза».

**Не входит:** бюджеты и ставки по спринтам — P04; Гант и цели спринта на главной — P06.

## P05 — баги и оперативные доработки, импорт «Прием обращений» (FR-07, FR-09) · ветка `claude/05-bugs-import`

**Миграция `0005_bug_flow.sql`:** `features.urgency` (low/medium/high/critical) и `features.fact_hours` (факт, только аналитика).

**Процесс бага — без новых состояний:**

| Поле бага | Где хранится |
| --- | --- |
| состояние | обычный статус с семантикой: new… → «не решено», in_progress/blocked → «в работе», done → «решено» (адаптер `BUG_STATE` в клиенте) |
| плановая дата устранения | `planned_end` |
| фактическая дата | `closed_at` |
| дата поступления | `requested_at` |
| ответственный | `assignee_name` |
| срочность | `urgency` — это не межотдельный голос |

- Баги не участвуют в планировании, ёмкости, релизах (см. P02/P03); спринт у них только справочный.
- Перевод в плановую задачу — кнопка «Перевести в плановую» в карточке (`PATCH task_kind='planned'`); справочный спринт при этом снимается.

**Источник:** таблица `1woBVsLqhRY67EYh8BJYGSqGSEeYPyWfmpUDN9bZ4T-E`.
- Заголовки прочитаны из реальной таблицы 13.10.2026. Вкладки: «Обращения», «Баги» (gid 0), «Доработки» (gid 1405337906), «Результаты по KPI…». Имя вкладки «Доработки» пишется с заглавной.
- Два источника формата `flat` (разные типы работ), пресеты `BUGS_CONFIG` и `IMPROVEMENTS_CONFIG` в `worker/domain/flatSheet.ts`. В «Синхронизации» есть кнопка «Подключить баги и доработки» (`bug_presets` в `GET /api/import/sources`).
- Стабильный ID — ключ Jira из колонки «задача в jira» (`id_pattern`). Без ссылки ID вычисляется из текста.
- Переименование строки не создаёт дубль. Повторный импорт без изменений даёт 0 изменений.

**Расширения формата `flat`** (TaskFlow выдаёт прежние колонки — новые добавляются только при маппинге):
- `kind`;
- `columns.status` + `status_map` (по умолчанию: Новый / В работе / Контроль / Блок / Готово / Отменён…);
- `columns.urgency` + `urgency_map`;
- `requested_at`, `initiator`, `author`, `extra[]` (дописываются в описание);
- `id_pattern`;
- `fact_hours_as: 'field'`.

Заголовки сравниваются без учёта регистра и переносов строк. Повторяющийся заголовок («Запрос от» ×2, «Комментарий» ×2) даёт первое непустое значение.

**Импортер (новые колонки Features):**
- `task_kind`, `initiator` (точное совпадение с отделом или пользователем, порядок слов в ФИО не важен; иначе свободный текст), `author` — только при создании карточки.
- `urgency`, `fact_hours` — описательные поля с 3-way diff: ручная правка не перетирается молча.

**Непроверено:** чтение реальной таблицы через сервисный аккаунт Worker. Локально проверено только на синтетическом CSV с теми же заголовками. После деплоя — «Проверить подключение» у обоих источников.

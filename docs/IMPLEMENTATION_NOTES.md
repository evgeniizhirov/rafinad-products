## P02 — основа модели задач (FR-02, FR-07 база, FR-10) · ветка `claude/02-task-foundation`

**Миграция `0003_task_foundation.sql`** (аддитивная), новые столбцы `features`:

| Столбец | Значение |
| --- | --- |
| `task_kind` | `planned` / `bug` / `operational_improvement`, по умолчанию `planned` |
| `is_product_internal` | 0/1 — скрытая задача Product. **Не связана** с `visibility` (`internal` = видна всем сотрудникам) |
| `initiator_type`, `initiator_user_id`, `initiator_department_id`, `initiator_name` | инициатор; `initiator_name` хранит свободный текст или снимок имени пользователя/отдела на момент выбора |

**Скрытые задачи — одно правило в `worker/lib/world.ts`:**
- `loadWorld(db, viewer, { includeInternal })` вырезает скрытые задачи и **все ссылающиеся строки**: голоса, оценки, теги, офферы, связи, релизы. Поэтому они не попадают ни в один список, счётчик, граф или агрегат — даже как плейсхолдер «скрыта».
- `includeInternal: true` действует только для product/admin и используется только в `GET /api/features` (`?internal=1|all`) и в карточке `GET /api/features/:ref`.
- Общие виды (overview, roadmap, priorities, releases, epics, offers, graph, planning) не показывают скрытые задачи никому, включая Product.
- `resolveFeature()` отдаёт 404 «Задача не найдена» всем, кроме product/admin. Это закрывает все write-маршруты (голоса, комментарии, связи, оценки, размещение).
- История карточки для не-editor отфильтровывает записи `relation_added`/`relation_removed`, где упоминается id скрытой задачи.
- `canSeeFeature(viewer, f)` — правило для одной задачи; `visibleFeatures(w, viewer, 'general'|'internal'|'all')`.
- Раскрытие (`is_product_internal` 1→0) требует `confirm_disclose: true`, иначе 409 `confirm_disclose`; изменение идёт в аудит.
- Скрыть задачу, которая входит в релиз, нельзя (400).

**Тип работы:**
- `isPlannable(f)` = `planned` и не скрытая.
- Только такие задачи участвуют в планировщике (`plannerInput`, `currentLoad`, `versions` плана), в ёмкости (`overloadFor`), в размещении по периоду (иначе 400) и в составе релиза (новые добавления — 400).
- Плановую задачу из релиза нельзя превратить в баг (400). Баг в плановую — можно.
- Баги видны в общих списках: это реальная работа. Фильтр — `?kind=bug,operational_improvement`.

**Инициатор:**
- API: `initiator: null | {type:'free_text', name} | {type:'user', user_id} | {type:'department', department_id}`.
- DTO для сотрудников: `initiator: {type, name, user_id?/department_id?, inactive?}`. Гостям поле не отдаётся.
- Фильтр `?initiator=user:<id>|department:<id>|text:<подстрока>|none`.
- `GET /api/users/directory` (product/admin) — только `id` и `name` активных пользователей, без email.

**UI:**
- Форма задачи: тип работы, «Внутренняя задача продукта», инициатор в трёх формах.
- Карточка: тип и инициатор. В списках — бейджи «Баг» / «Оперативная доработка» / «Внутренняя продукта».
- Бэклог: фильтры типа, «Внутренние задачи продукта» (только product/admin), инициатора по отделу.

**Локальные миграции:** `scripts/sqlite-d1.ts → migrate()` теперь ведёт `d1_migrations` и применяет только недостающие миграции. `npm run dev:node` обновляет существующую `.local/dev.sqlite`. Проверено на копии с 61 задачей: все получили `planned`.

**Не входит:** процесс багов (срочность, состояние, даты устранения) — P05; спринты — P03.

## P03 — спринты, релизы, месяцы, фокус (FR-06, фокус из FR-03) · ветка `claude/03-sprint-calendar`

**Миграция `0004_sprint_calendar.sql`:**
- `releases.cycle_number` — номер цикла, уникальный, если задан; у старых релизов NULL.
- `sprints` — `release_id`, `ordinal` 1/2, `code` «8.1», даты, `status` planned/active/closed; уникальность `(release_id, ordinal)` и `code`; CHECK на порядок дат.
- `accounting_months` — `month` YYYY-MM (уникальный), 1-е — последнее число, `budget_limit_rub` на будущее (P04), `status`.
- `features`:
  - `sprint_id` — для плановых задач это план спринта, для багов только справка;
  - `planned_production_date`;
  - `baseline_production_date` — первое обещание, при переносах не меняется (нужно для FR-11);
  - `is_focus`.
- Настройки: `calendar_anchor_date=2026-10-07`, `calendar_anchor_release=8`, `calendar_releases_ahead=3`, `calendar_months_ahead=12`. Администратор меняет их через `PUT /api/admin/settings`.

**Совместимость:** `capacity_periods` и `features.period_id` не тронуты, планировщик работает как раньше. Автоматического сопоставления «период → спринт» нет: такие задачи перечислены в `GET /api/calendar → unmapped` и на странице «Спринты».

**Домен `worker/domain/calendar.ts`** (чистые функции):
- `releaseCycle(anchor, n)` — спринт 14 дней ср–вт, тест с +1 дня, прод через +9 дней после конца спринта.
- `cycleOn`, `monthDates`, `addMonths`.
- `planGeneration(anchor, existing, {today, releasesAhead, monthsAhead})`:
  - окно — от опорного релиза до текущего + N вперёд, по месяцам аналогично;
  - существующие записи пропускаются, а не двигаются;
  - вручную изменённый спринт попадает в отчёт;
  - пересечение даёт конфликт, а не дубль.

**API (`worker/routes/calendar.ts`):**

| Маршрут | Доступ | Что делает |
| --- | --- | --- |
| `GET /api/calendar` | все; гости — только публичные релизы, без месяцев | релизы-циклы со спринтами, месяцы, текущий спринт, `unmapped` для product/admin |
| `GET /api/sprints`, `GET /api/sprints/:id` (id или код «8.1») | все | `features` — план, `reference` — справочные баги |
| `POST /api/calendar/generate-preview` → `{plan, plan_hash}`; `POST /api/calendar/generate {plan_hash}` | product/admin | генерация; при изменении календаря после предпросмотра — 409 `stale`; идемпотентно; уникальные индексы защищают от параллельного запуска |
| `PATCH /api/sprints/:id` | product/admin | исключение: даты/статус, причина обязательна, пересечения запрещены. Задачи, у которых срок совпадал со старым сроком выкладки спринта, и `releases.planned_date` (для спринта 2) следуют за новым сроком. `baseline` не меняется |
| `PATCH /api/features/:id/schedule {release_id?, sprint_id, planned_production_date?, version, confirm_approved_change?, reason?}` | редакторы | см. ниже |

Правила `PATCH /api/features/:id/schedule`:
- Плановая задача: спринт задаёт релиз (`release_features` синхронизируется), дата выкладки = срок спринта, если не задана явно.
- Перенос пишется в аудит как `rescheduled` (спринт `8.1 → 8.2`, новая дата).
- Изменение состава утверждённого релиза — 409 `approved` без подтверждения и причины.
- Баг или доработка: только справочный `sprint_id`; релиз — 400; дата не трогается.
- Внутренние задачи продукта: 400.

**Прочее:**
- Если задача убрана из релиза через `PUT /api/releases/:id/features`, её спринт и плановая дата сбрасываются.
- Сводка релиза дополнена: `cycle_number`, `sprints[]` (по каждому — задач/готово), `focus_count`, `focus_done`. Готовность считается по обоим спринтам: первая выкладка релиз не закрывает.
- `is_focus` допустим только для плановой общей задачи; задача, переставшая быть плановой, теряет фокус.
- Фильтры бэклога: `?sprint=<id|none>`, `?focus=1`.

**UI:**
- Раздел «Спринты» (`/calendar`): таблица релизов со спринтами и датами, месяцы, предпросмотр генерации, список несопоставленных задач.
- Карточка, вкладка «Ресурсы»: блок «Релиз, спринт и выкладка» (или «Спринт (справочно)» для багов). Во вкладке «Описание» — «Релиз → спринт», плановая выкладка и первое обещание.
- Форма: чекбокс «Фокусная задача релиза».

**Не входит:** бюджеты и ставки по спринтам — P04; Гант и цели спринта на главной — P06.

**Миграция `0006_business_blockers.sql`:** таблица `feature_blockers`.

**`GET /api/overview`** — новые поля, старые сохранены:
- `gantt[]`:
  - только семантика `analysis`/`in_progress` и есть срок окончания работ;
  - конец = `planned_end`, а для плановой задачи в спринте без `planned_end` — конец разработки спринта (`end_source: 'sprint'`);

  - берётся ближайший открытый релиз, где есть фокусные задачи (иначе просто ближайший);

  - бизнес-блокеры: что ждём, от кого, с какого числа, сколько дней, просрочен ли ответ, что разблокирует;
  - затем технические: зависимость или статус «Заблокирована» без указанной причины;
  - гость видит только задачу, без деталей ожидания.

## P07 — персональные API-ключи (FR-01) · ветка `claude/07-api-keys`

**Миграция `0007_api_keys.sql`:**
- таблица `api_keys`: `prefix` (уникальный, публичная часть), `secret_hash` (sha256 всего токена), `scopes` (JSON), `expires_at`, `revoked_at`/`revoked_by`, `last_used_at`, `use_count`, окно лимита;
- столбец `audit_log.api_key_id`.

**Формат токена:** `rr_<prefix 8>_<secret 40>`. Токен показывается один раз в ответе `POST /api/me/api-keys` и нигде не логируется.

**Middleware** (`worker/index.ts` → `loadApiKeyUser` + `scopeFor` в `worker/lib/auth.ts`):
- при заголовке `Authorization` cookie игнорируется;
- ключ невалиден, отозван или просрочен, либо владелец отключён — 401 `invalid_api_key`;
- больше 120 запросов в минуту — 429;
- маршрут недоступен ключам — 403;
- у ключа нет нужного scope — 403;
- затем, как обычно, роль (`perms.*`) и видимость. Пользователь, роль и членство в отделах перечитываются на каждом запросе.

Что недоступно ключам:
- `perms.admin` и `perms.overrideVote` всегда ложны: ключ администратора не открывает админку и не меняет чужие голоса;
- `scopeFor` → `null` для `/api/me/api-keys`, админки, импорта, планирования, авторизации.

**Добавляя новые маршруты, обновите `scopeFor`** — иначе ключи получат 403. Экспорт P08 уже размечен как `exports:read`.

**Аудит:** `auditStmt` пишет `api_key_id` из `actor.apiKey`. Автор задачи, созданной ключом, — его владелец; инициатор указывается явно (T18).

**API:** `GET/POST /api/me/api-keys`, `DELETE /api/me/api-keys/:id` (только из браузерной сессии); `GET /api/admin/api-keys`, `POST /api/admin/api-keys/:id/revoke {reason}`.

**UI:** раздел «API-ключи» в профиле (новый ключ с показом токена один раз), вкладка «API-ключи» в администрировании.

**Документация:** `docs/API_KEYS.md` — подключение Claude Code и Codex, curl-примеры.

## P04 — бюджет по месяцам и ставки команд (FR-05) · ветка `claude/04-monthly-budget`

В стопке идёт после P08: порядок другой, чем в плане, потому что P04 зависит только от P03.

**Миграция `0009_budget.sql`:**

| Таблица / настройка | Что хранит |
| --- | --- |
| `team_rates` | версии ставок: `effective_from` = начало спринта (UNIQUE `team_id + effective_from`); строки не редактируются, новая версия перекрывает старую |
| `month_capacities` | ~~часы команды на месяц~~ — заменено на `sprint_capacities` миграцией 0011 (решение 13.10), таблица удаляется |

**Модель (`worker/domain/budget.ts`):**
- Стоимость задачи = Σ часов платных команд (`include_in_budget`) × ставка, действующая на **начало спринта задачи**.
- Учитываются только плановые, не скрытые, не отменённые задачи **со спринтом**. Баги и доработки в план не входят.
- Нет оценки платной команды → стоимость помечается «неполная»; явный 0 — работы нет.
- Распределение по месяцам: интервал работ задачи (`planned_start..planned_end`, если оба заданы, иначе даты спринта) делится пропорционально рабочим дням (`workdays`) или календарным (`calendar_days`). Выбор хранится в настройке `budget_allocation` (решение 13.10: лимит задаётся на каждый календарный месяц, способ деления не менялся — `workdays`). Результат всегда помечен `forecast: true`. Спринт 8.2 даёт 80% октябрю и 20% ноябрю.
- Закрытие месяца (`POST /api/planning/months/:month/close`) пишет снимок; дальше отчёт по месяцу берётся из снимка. Изменение ставки с будущего спринта его не меняет.

**Проверка при планировании (ручной режим):**
- `PATCH /api/features/:id/schedule`: если вход задачи в спринт превышает месячный лимит ₽ **или** доступность команды в целевом спринте (с 13.10; было — в месяце) — 409 `over_budget` со списком превышений.
- С `confirm_over_budget` + `reason` — сохраняется, в аудите `is_override = 1`.
- Утверждённые составы не пересчитываются.
- Старый планировщик по `capacity_periods` не менялся — переход на месяцы и спринты делается отдельной задачей.

## P09 — аналитика (FR-11) · ветка `claude/09-analytics`

**Миграция `0010_analytics.sql`:**
- индекс `idx_audit_entity_action`;
- настройка `analytics_high_priority = 4` — порог «высокого приоритета». Решено 13.10: оставить 4 на время тестирования. Меняется через `PUT /api/admin/settings`; отдельного поля в UI админки пока нет.

**Источник истории — `audit_log`:**
- Отдельной таблицы истории статусов нет. Переходы берутся из записей `updated` / `import_updated` с полем `status_id`.
- История считается надёжной только если у задачи есть запись `created` или `import_created`.
- У задач без такой записи (демо-данные, данные до запуска приложения) истории нет. Они попадают в `insufficient` / `no_history`, а не в «0» и не в «не откладывалась».
- Начальный статус = `from` первого перехода (или текущий статус, если переходов не было).

**Формулы (`worker/domain/analytics.ts`, всё по `semantic` статуса — переименование статуса цифры не меняет):**

| Показатель | Как считается |
| --- | --- |
| поступило | `requested_at ?? created_at` в периоде |
| сделано за период | semantic `done` и `closed_at` в периоде |
| просрочено | открытая задача, срок < сегодня. Срок плановой = `planned_production_date ?? planned_end`, бага/доработки = `planned_end` |
| заблокировано | semantic `blocked` или есть открытая бизнес-блокировка |
| в срок, % | среди сделанных за период с `baseline_production_date`: `closed_at ≤ baseline`. Без baseline — отдельный список |
| время цикла | первый переход в `analysis`/`in_progress` → последний переход в `done`, в днях. Медиана, p75, p90 отдельно для багов+доработок и для плановых. При n < 3 — `insufficient` |
| блокировки по владельцам | открытые `feature_blockers`: число, сумма дней с `started_at`, просроченные по `due_at` |
| дисциплина релиза | фокусные задачи релизов с прошедшей `planned_date` в периоде: доля сделанных до даты релиза |
| кто создаёт | поступившие за период по `created_by` (автор) и отдельно по инициатору. `via_api_key` = запись `created` с `api_key_id` |
| спрос | только плановые с голосами. `high` = score ≥ порога, `strictly_5`, `high_unresolved` (не done/cancelled/postponed), конверсия по semantic |
| «востребованные сделаны без переносов» | high + done, в истории нет перехода в `postponed`/`cancelled`. Без истории — счётчик `no_history` |

**Права:**
- `GET /api/analytics/summary?from&to&<фильтры бэклога>` — любой вошедший пользователь, а также API-ключ со scope `tasks:read`.
- Считается только по задачам, видимым этому пользователю.
- Параметр `internal` удаляется: скрытые задачи Product не входят в аналитику ни для какой роли, даже для Product.
- Каждый показатель возвращает `{value, ids, insufficient?, extra?}`.
- Drill-down: `/backlog?ids=a,b,c`. Новый фильтр `ids` в `queryFeatures`; сервер снова применяет все ACL. Клиент передаёт не больше 400 id.

**UI:**
- раздел «Аналитика»: период, тип задач, пресеты 30/90 дней;
- плитки кликабельны;
- таблицы «Кто создаёт задачи» (инициатор / автор) и «Блокировки по владельцам» — строки кликабельны;
- полосы по статусам.

В бэклоге фильтр `ids` показывается чипом «Из аналитики: N задач».

**Ограничения / дальше:**
- Нет истории оценок приоритета: `department_votes` хранит только текущий балл. «Был высокий, потом снизили» не видно.
- Импорт пишет смену статуса в `import_updated` (тот же формат `{field, old, new}`), поэтому она попадает в историю. У flat-источников (TaskFlow, баги) статус следует таблице автоматически. У остальных статус защищён и меняется только при ручном разрешении конфликта. Задачи, загруженные до P09, но созданные импортом, историю имеют: `import_created` был и раньше.
- Для > 400 задач drill-down открывает первые 400. Лучше заменить на drill-down по фильтрам + метрике (`/backlog?metric=…&from&to`).

## v2-04 — импорт внешних ссылок · ветка `claude/v2-04-link-import` (без миграции)

- «Баги» и «Доработки»: `links: {'задача в jira': 'jira'}`, `links_from_text: true`. Колонка «задача в jira» по-прежнему даёт устойчивый ID (ключ Jira), в описание больше не дублируется.

**Чтение:**
- `flatToCanonical` выдаёт каноническую колонку `links` (строка = `kind\turl\tcolumn`).

- CSV и публичная ссылка (gviz) — только видимый текст; в предпросмотре об этом есть заметка.
- **Ни одного запроса к Jira, Bitrix24 или Confluence** (тест проверяет хосты: только `oauth2.googleapis.com` и `sheets.googleapis.com`).

**Сравнение** (`worker/domain/linkImport.ts`, `planLinks`):

| Ситуация | Результат |
| --- | --- |
| URL нет в карточке | `add` (origin `import`, `source_id`, колонка) |
| URL уже есть ручной или из другого источника | `kept`, не трогается |
| ссылка этого источника, тот же тип | `unchanged` |
| ссылка этого источника, тип изменился в таблице | `update`; если ссылку меняли вручную (`locally_edited`) — `conflict`, по умолчанию остаётся версия системы |
| ссылка этого источника пропала из таблицы | `missing` («нет в источнике»), **не удаляется**; удаляется только отмеченная в предпросмотре |
| пустая ячейка | ручные ссылки не трогаются никогда |

- План показывается в предпросмотре (`item.payload.link_plan`, сводка `run.links`) и **пересчитывается на свежих данных при применении**.
- Добавление — `INSERT OR IGNORE`: ссылка, добавленная вручную между предпросмотром и применением, не дублируется.
- Решения в `resolution.links = { source: [url], remove: [url] }`. Сервер проверяет, что URL действительно в конфликте или «нет в источнике» — ручную ссылку выбрать для удаления нельзя.
- Аудит на задачу: `import_links`. Итоги применения — `counts.links`.

**Устойчивый ID TaskFlow** (ТЗ §3 просит проверить):
- без колонки ID это `tf-` + хеш нормализованного текста ячейки «Задача» + исполнителя;
- импорт ссылок его не меняет;
- переименование или смена исполнителя в таблице дают новый ID и «возможный дубль» в предпросмотре — то же, что и раньше;
- исправление — пункт 7.5 ТЗ (отложен владельцем). У источников «Баги» и «Доработки» ID — ключ Jira из ссылки, он устойчив.

- **План:**
  - Разработка — `planned_start`…`planned_end` задачи, если оба заданы, иначе даты спринта;
  - QA — `testing_start`…`production_due` спринта;
  - Выкладка — веха: `planned_production_date`, иначе `production_due`; у бага без спринта — `planned_end`;
  - Продукт и Дизайн — без плана, только факты.
- **Без спринта и дат план пустой** — ничего не выдумывается.
- **Состояние этапа:**

| Состояние | Когда |
| --- | --- |
| `done` | есть подтверждённое завершение, или задача в статусе «Завершена» |
| `active` | этап начат |
| `unconfirmed` | дата начала по плану прошла, а начало не подтверждено — это риск, а не прогресс |
| `skipped` | этап не трогали, а следующий уже начат |
| `not_started` | иначе |

- **Прогноз незавершённого этапа:** прогноз Product, иначе конец плана; если срок прошёл — продолжение до «сегодня» с риском. Выкладка сдвигается, если предыдущие этапы закончатся позже неё.

- `agreed` = есть исходный план. Плановая задача в спринте без него — «не согласовано».

**Когда фиксируется исходный план:**
- `POST /api/releases/:id/approve` — всем плановым задачам релиза без исходного плана;
- изменение состава утверждённого релиза (подтверждённое), в том числе назначение в спринт утверждённого релиза;
- `POST /api/features/:id/baseline {reason}` — новая ревизия, только product/admin; старые ревизии остаются.

Первая ревизия заполняет `features.baseline_production_date` — «первое обещание» для аналитики.

## v2-08 — удаление навсегда · ветка `claude/v2-08-hard-delete` (миграция 0016)

**Решения:**
- ТЗ §5: удалять навсегда может только администратор, по одной записи, после предпросмотра последствий и ввода ключа записи;
- решение владельца 13.10 №14: история удалённой записи стирается, копии не хранятся, остаётся одна запись журнала о факте удаления.

**Объекты:** задача, эпик, предложение. Справочники, пользователи, релизы и источники импорта не удаляются: у них исторические связи, это отдельное решение. Массового удаления нет.

**Скрыть вместо удаления** — прежними средствами: статус «Отменена», видимость «Черновик», предложение «Отклонено». В диалоге удаления об этом есть подсказка.

**API** (`worker/routes/purge.ts`). Доступ только `perms.admin`: роль admin в браузерной сессии; API-ключ не подходит.
- `GET /api/admin/purge/:kind/:ref` (kind — `feature | epic | proposal`, ref — id или ключ `RF-12` / `EP-3` / `P-5`) возвращает:
  - `key`, `title`, `version`, `merged` (объединённые дубли);
  - `effects[]` — `{label, count, items?, note?}`;
  - `warnings[]`, `confirm` (что ввести), `backup` (как восстановить).
- `POST /api/admin/purge/:kind/:ref {confirm, version, reason?}`:
  - неверный ключ — 400; запись изменилась после предпросмотра — 409;
  - всё выполняется одной транзакцией D1.

**Задача:**
- Удаляются вместе с ней:
  - её объединённые дубли (рекурсивно);
  - теги, оценки, голоса, состав релиза, комментарии, блокировки, внешние ссылки, связи с предложениями;
  - исходный план, факты и прогнозы этапов;
  - связи с другими задачами в обе стороны;
  - `plan_alerts`, все её записи `audit_log`.
- Импорт:
  - строки `import_items` с копиями задачи стираются;
  - `source_entity_links` заменяются надгробиями.
- Закрытые месяцы бюджета (`month_snapshots`): суммы не меняются, строка задачи обезличивается («Удалённая задача», без id).
- Связанные задачи и предложения остаются.

**Эпик:** задачи остаются без эпика; в их историю пишется, куда делся эпик. Импорт обрабатывается так же, как у задачи.

**Предложение:** удаляются его дубли, голоса, связи с задачами и комментарии. Задачи остаются.

**Журнал:** одна запись `deleted_permanently` — ключ, название, ключи дублей, кто, когда, причина. Описания, приватных заметок и комментариев в ней нет.

**Номера не переиспользуются:** `app_settings` `number_floor.features | epics | proposals` хранит наибольший удалённый номер. `lib/numbers.ts#nextNumber` используется при создании задач, эпиков, предложений и при импорте.

**Надгробия импорта** (`import_tombstones`, миграция 0016):
- ключ — `(source_id, entity_type, external_id)`, плюс `entity_key`, `deleted_at`, `deleted_by`; без названия и содержимого;
- в предпросмотре синхронизации такая строка — `action: create`, решение `skip`, предупреждение «удалена администратором», `payload.tombstone`;
- в интерфейсе метка «удалена администратором (RF-12)» и кнопка «Восстановить импорт» (решение `create`);
- при применении создаётся новая карточка с новым номером, надгробие удаляется, в журнал пишется `restored_after_delete`;
- сопоставление по бизнес-ID в другом источнике надгробием не блокируется: надгробие действует только для источника, из которого запись была загружена.

**Резервная копия:** отдельные копии не хранятся (решение №14). Вернуть данные можно только восстановлением всей базы через Cloudflare D1 Time Travel (до 30 дней); диалог об этом предупреждает.

## v2-09 — конструктор экспорта · ветка `claude/v2-09-export-builder` (миграция 0017)

**Спецификация** `{ columns: [{field, title?}], query, sort: [{field, dir}] (до 3), groups: [] (до 2), subtotals }`:

**Таблица** (`worker/domain/exportBuild.ts`, чистая функция):

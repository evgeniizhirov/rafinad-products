# Rafinad Product Roadmap

Веб-приложение для продуктового бэклога платформы Rafinad: карточки доработок, эпики, приоритеты от подразделений, оценка часов ресурсных команд, предлагаемый план по периодам, роадмап и релизы. Опубликованные данные доступны без входа, любые изменения — только после входа и с проверкой прав на сервере.

Это инструмент продуктового планирования, а не таск-трекер разработчиков. Интеграций с Jira, Confluence и корпоративной CRM нет и не планируется.

## Архитектура

| Слой | Технология |
| --- | --- |
| Хостинг | Cloudflare Workers, один Worker `products-roadmap` (API и статика) |
| База данных | Cloudflare D1 (SQLite), SQL-миграции в `migrations/` |
| API | TypeScript, собственный маленький роутер (`worker/lib/http.ts`), валидация `zod` |
| Интерфейс | React 19, собирается `esbuild` в `dist/client`, собственная CSS-система (`client/src/styles.css`) |
| Авторизация | email + пароль, серверные сессии в D1, cookie `HttpOnly; Secure; SameSite=Lax`, PBKDF2-SHA256 |
| Импорт | Google Sheets API (scope `spreadsheets.readonly`, JWT сервисного аккаунта подписывается в Worker) и CSV |
| Тесты | встроенный тест-раннер Node + `node:sqlite` вместо D1 (тот же SQLite и та же схема) |

Почему не Next.js + PostgreSQL из рекомендаций ТЗ: приложение размещается в Cloudflare Workers, где нативная база — D1. Все требования ТЗ к данным (транзакционный импорт, optimistic locking, журнал) реализованы на D1: `batch()` в D1 выполняется как одна транзакция.

```
worker/
  index.ts            точка входа: /api/* → роутер, остальное → статика (+ заголовки безопасности)
  domain/             чистая логика без ввода-вывода: приоритеты, граф зависимостей, планировщик,
                      загрузка команд, движок импорта, CSV, нормализация текста
  lib/                http, db (транзакции, guard-условия), auth, crypto, audit, google, world (DTO)
  routes/             auth, admin, features, merge, priorities, catalog (эпики), releases,
                      planning, dashboard (обзор/роадмап), imports
client/src/           React-интерфейс (pages/, features.tsx, ui.tsx, lib.ts)
migrations/           схема D1
scripts/              сборка клиента, seed, локальный dev-сервер на Node, создание администратора
seed/seed.sql         демонстрационные данные (генерируется scripts/gen-seed.ts)
samples/*.csv         шаблон таблицы для импорта (те же данные, что у демо-источника)
tests/                автотесты
```

### Модель данных

`users, roles, sessions, invites, login_attempts, departments, department_memberships, resource_teams, categories, statuses, stages, app_settings, epics, features, feature_tags, feature_estimates, feature_relations, department_votes, releases, release_features, comments, audit_log, sheet_sources, import_runs, import_items, import_apply_locks, source_entity_links, sprints, accounting_months, sprint_capacities, team_rates, feature_blockers, feature_links, proposals (+ votes, features, comments), feature_plan_baselines, feature_phase_events, feature_phase_forecasts, import_tombstones, export_templates, api_keys, export_runs`. Старые плановые периоды (`capacity_periods`, `team_capacities`, `plan_runs`, `plan_alerts`) удалены миграцией 0018 (vNext v2-10).

- **Статус и этап — разные поля.** У статуса есть смысловая группа (`new`, `analysis`, `ready`, `planned`, `in_progress`, `blocked`, `postponed`, `done`, `cancelled`). Благодаря ей администратор может переименовывать статусы и добавлять свои, не ломая планировщик и дату завершения.
- **Связи:**
  - `belongs_to_epic` — `features.epic_id`;
  - `blocks`, `related_to`, `duplicate_of` — таблица `feature_relations`, циклы `blocks` запрещены.
- **Приоритет принадлежит отделу.** На пару «отдел + задача» хранится одна текущая оценка 1–5, отсутствие оценки ≠ 1. Все изменения пишутся в `audit_log`.
- **Optimistic locking.** У изменяемых сущностей есть поле `version`. Позднее сохранение со старой версией получает ответ `409` и не перезаписывает чужие изменения.
- **Атомарность.** Многошаговые операции выполняются одним `D1 batch` с guard-условиями (таблица `_guard`). Если предусловие нарушено, вся транзакция откатывается.

## Запуск локально

Нужен Node.js ≥ 22.5.

```bash
npm install

# Вариант 1 — без Cloudflare: настоящий код Worker на Node + SQLite-файл .local/dev.sqlite
ADMIN_EMAIL=you@company.ru ADMIN_PASSWORD='Сложный-пароль-1' npm run dev:node
# → http://localhost:8788 (при первом запуске создаются схема, демо-данные и администратор)

# Вариант 2 — wrangler dev с локальной D1
cp .dev.vars.example .dev.vars
npm run db:migrate:local
npm run db:seed:local
npx tsx scripts/create-admin.ts you@company.ru "Ваше Имя" > .local/admin.sql
npx wrangler d1 execute DB --local --file .local/admin.sql   # временный пароль выводится в консоль
npm run dev                                                   # → http://localhost:8787
```

Демо-пользователи из seed (`*@rafinad.test`) создаются без паролей. Доступ им выдаёт администратор: «Администрирование → Пользователи → Сбросить доступ».

## Деплой

Workers Builds собирает и деплоит Worker при каждом push в `main`.

1. Cloudflare Dashboard → **Workers & Pages → products-roadmap → Settings → Builds → Connect**, репозиторий `rafinad-products`, ветка `main`.
2. **Build command** — пусто, **Deploy command** — `npm run deploy` (подойдёт и `npx wrangler deploy` по умолчанию).

Клиент собирается сам: на шаге `npm install` (`postinstall`) и ещё раз внутри `npm run deploy`. Настройку `build.command` из `wrangler.jsonc` Workers Builds не выполняет, поэтому на неё не полагаемся.

**Миграции D1 в сборке не запускаются.** Токен, который Workers Builds создаёт по умолчанию, не имеет прав на D1. Новые миграции применяйте отдельно: `npm run db:migrate:remote` (локально, после `npx wrangler login`). Другой вариант — выдать токену сборки право **D1: Edit** и указать Deploy command `npm run deploy:with-migrations`.

Вручную, без Workers Builds: `npx wrangler login && npm run deploy`.

## Google Sheets: read-only доступ

1. Google Cloud Console → создать проект или выбрать существующий → включить **Google Sheets API**.
2. **IAM → Service Accounts → Create**. Роли проекту не нужны. Затем **Keys → Add key → JSON** — скачать ключ.
3. Сохранить ключ как секрет Worker (только на сервере, в репозиторий не попадает):
   ```bash
   npx wrangler secret put GOOGLE_SERVICE_ACCOUNT_JSON   # вставить содержимое JSON одной строкой
   ```
4. В Google-таблице: **Настройки доступа** → добавить email сервисного аккаунта (`…@….iam.gserviceaccount.com`) с ролью **«Читатель»**. Права редактора не нужны: приложение запрашивает только scope `spreadsheets.readonly`.
5. В приложении: **Синхронизация → Добавить источник** → вставить ссылку на таблицу → «Проверить подключение» → «Синхронизировать» → разобрать предпросмотр → «Применить изменения».

Без сервисного аккаунта читаются только таблицы с доступом «Все, у кого есть ссылка — читатель». Для закрытой таблицы есть обходной путь: скачать лист как CSV (Файл → Скачать → CSV) и нажать у источника **«Из выгрузки CSV»** — дальше обычный предпросмотр и применение (запуск помечается `origin = 'file'`).

Секрет можно добавить и без wrangler: Cloudflare Dashboard → Workers & Pages → `products-roadmap` → **Settings → Variables and Secrets → Add** → тип **Secret**, имя `GOOGLE_SERVICE_ACCOUNT_JSON`, значение — содержимое JSON-ключа.

### Формат «одна таблица задач» (TaskFlow)

Источник с `config.format = 'flat'` читает один лист задач и сам переводит его в карточки. Соответствие колонок задаётся в настройках источника; для листа **TaskFlow** отчёта по загруженности оно заполнено заранее:

| Колонка листа | Куда попадает |
| --- | --- |
| `Задача` | название (первая строка ячейки); ссылки и остальные строки — в описание. Ячейка только со ссылкой на портал → «Задача портала № …» |
| `Комментарий`, `Факт в часах` | описание |
| `Категория` | категория (по названию справочника) |
| `Сотрудник` | исполнитель; есть исполнитель → «В работе», нет → «Новая» |
| `Новый срок` / `Изначальный срок` | срок (`ДД.ММ` — ближайший год, `ДД.ММ.ГГГГ`) |
| `Сделано`, `Дата выполнения` | «Да» → «Завершена» с датой закрытия |
| `Приоритет` | тег `P1`, `P2`… (голоса отделов синхронизация не трогает) |
| `Влетевшая` | тег `влетевшая` |
| `Оценка в часах` | часы команды Product |

ID задачи вычисляется из текста задачи и исполнителя (`tf-…`), поэтому перестановка строк и правка остальных колонок обновляют ту же карточку. Переименованная или переназначенная задача приходит как «возможный дубль» — её привязывают к прежней карточке (кнопка «Дубли с точным совпадением названия — привязать»). Две одинаковые строки с одним исполнителем — ошибка второй строки. Если в таблицу добавить колонку с постоянным ID и указать её в настройках, она используется вместо вычисляемого ID. Статус у такого источника следует колонке «Сделано», пока его не меняли в системе; изменённый вручную статус защищён.

### Формат «шаблон из 4 листов»

Шаблоны с примерами строк лежат в `samples/` и скачиваются из раздела «Синхронизация». Имена листов настраиваются в источнике.

| Лист | Колонки |
| --- | --- |
| `Epics` | `external_id`*, `title`*, `description`, `category`, `status`, `visibility` |
| `Features` | `external_id`*, `title`*, `description`, `category`, `epic_external_id`, `status`, `stage`, `requested_at`, `<код команды>_hours`…, `visibility` |
| `Relations` | `from_type`, `from_external_id`, `relation_type` (`blocks`, `related_to`, `duplicate_of`, `belongs_to_epic`), `to_type`, `to_external_id` |

`*` — обязательные колонки.

- Колонки часов определяются по коду ресурсной команды (`backend_hours`, `design_hours`…). Колонки с другими названиями сопоставляются в настройках источника.
- Даты — `ГГГГ-ММ-ДД` или `ДД.ММ.ГГГГ`.
- Лишние колонки игнорируются.

### Правила синхронизации

- Предпросмотр ничего не меняет в бэклоге. «Применить» записывает все принятые изменения одной транзакцией.
- Повторное применение того же предпросмотра отклоняется. Если таблица изменилась после предпросмотра, применить устаревший результат нельзя — нужно сформировать новый.
- Порядок сопоставления: пара `(источник, external_id)` → точный бизнес-ID (`external_ref`) → нормализованное название и сходство текста. Похожие карточки **не объединяются автоматически**: пользователь выбирает существующую карточку, новую или пропуск.
- Описательные поля (название, описание, категория, эпик, связи) сравниваются трёхсторонне: последнее импортированное значение, значение в системе и значение в таблице. Если поле поменялось и в системе, и в таблице, это конфликт — пользователь выбирает, какое значение оставить.
- Синхронизация никогда не перезаписывает голоса отделов, утверждённые релизы, плановые периоды, комментарии, права и публикацию. Статус, этап и вручную уточнённые часы обновляются только при явной отметке в предпросмотре.
- Если строка исчезла из таблицы, карточка не удаляется. Новые карточки попадают в черновики или сразу во внутренние — по настройке источника. Ячейки проверяются и хранятся как текст: HTML и формулы не исполняются.

## Роли

| Роль | Может |
| --- | --- |
| Гость (без входа) | смотреть опубликованные карточки, эпики, приоритеты, роадмап, релизы |
| Руководитель отдела | всё публичное и внутреннее (кроме черновиков); голосовать за свои отделы; комментировать |
| Продуктовая команда | создавать и редактировать задачи, эпики, связи, оценки, план, релизы; запускать импорт; голосовать за свои отделы |
| Администратор | всё перечисленное, а также пользователи, роли, справочники, веса, настройки публикации, журнал. Изменить оценку за чужой отдел может только с указанием причины — в журнале это отмечается как административное действие |

## Реализовано

- Публичный режим с отдельными урезанными DTO.
  - Скрытые связанные задачи отображаются без названия.
  - Агрегаты для гостей считаются только по опубликованному.
  - Оценки часов и загрузка команд публикуются по настройке.
- Локальная авторизация:
  - приглашения и временные пароли с обязательной сменой;
  - ограничение попыток входа, выход, отключение пользователя;
  - защита последнего администратора;
  - проверка `Origin` для изменяющих запросов.
- Справочники без правки кода: отделы с весами и отделом Product, ресурсные команды, категории, статусы со смысловыми группами, этапы, плановые периоды.
- Каталог:
  - CRUD задач и эпиков;
  - дерево эпиков с часами и прогрессом;
  - связи и запрет циклов, граф зависимостей;
  - комментарии, полная история изменений;
  - объединение дублей с явным выбором конфликтующих оценок и сохранением старой ссылки.
- Приоритизация:
  - голоса 1–5, взвешенный балл, устойчивая сортировка при равенстве;
  - матрица «задачи × отделы», режим «интересы отдела».
- Ресурсы:
  - ёмкость команд по периодам;
  - загрузка, остаток, процент и дефицит;
  - перенос задачи в перегруженный период только с подтверждением и причиной.
- Планирование по спринтам (vNext): «Планировщик» продуктовой команды — очередь по приоритету, спринты, часы команд против ёмкости, бюджет месяцев; изменение утверждённого релиза и превышение бюджета требуют причины. Старый автопланировщик по периодам и «Роадмап» по периодам удалены (v2-10).
- «Обзор» с общим Гантом: релизы → спринты → задачи, у каждой задачи свои этапы (план, исходный план, факт, прогноз, отклонение); релизы (список, календарь, состав, готовность, блокировки, утверждение).
- Импорт из Google Sheets и CSV с предпросмотром, дублями, конфликтами и защищёнными полями. Импорт атомарный и идемпотентный, ведётся журнал.

## Известные ограничения MVP

- Пароли хешируются PBKDF2-SHA256 (100 000 итераций — максимум WebCrypto в Workers), а не Argon2id: Argon2 в WASM упирается в лимиты CPU Worker. Формат хеша версионирован, алгоритм можно сменить без миграции пользователей.
- Вся оценка задачи относится к одному спринту; для объёмных задач используйте разбиение на этапы или связанные задачи.
- Если у задачи есть хотя бы одна оценка, команды без оценки показываются как «не оценено», но планировщик считает их ненужными. Чтобы явно указать, что команда не нужна, поставьте 0.
- Синхронизация запускается только вручную, двусторонней синхронизации и расписания нет.
- Отправки писем нет: ссылку-приглашение или временный пароль администратор передаёт сам.
- Интерфейс рассчитан в первую очередь на десктоп; на телефоне доступен просмотр и основные действия.
